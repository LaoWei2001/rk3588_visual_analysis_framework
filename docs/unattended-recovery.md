# 现场无人值守与故障恢复

当前目标是两类设备级故障：**操作系统崩溃或整机卡死**，以及**系统仍运行但网络失联**。
侧边栏“故障恢复”分为“系统故障恢复”“网络故障恢复”和可选的“程序故障恢复”。网页负责设置和显示；实际恢复由
系统服务和硬件完成，不依赖浏览器、Web 后端或视觉程序心跳。

视觉应用异常退出和业务处理停滞不作为默认恢复条件。`app_restart_enabled` 和
`app_stall_enabled` 默认均为 `false`，用户可在独立的“程序故障恢复”分类开启，见
[程序恢复操作说明](application-recovery.md)。保存设置不重启程序，需立即应用时再由用户点击明确的重启按钮。
已有配置不会因更新代码自动被覆盖。

## 整机卡死与系统崩溃

| 情况 | 恢复机制 | 本板当前配置 |
| --- | --- | --- |
| 内核报告严重错误，仍能执行重启代码 | 内核 panic 自动重启 | 约 10 秒后尝试软件重启 |
| 系统卡死，PID 1 无法继续喂硬件看门狗 | 硬件看门狗超时复位 | DW 看门狗实际约 89 秒 |
| 系统仍在喂狗，但网络失联 | 独立网络恢复服务 | 需用户配置目标并开启网络策略 |

89 秒从最后一次成功喂狗算起，不是从 SSH 断开时算起；系统启动和网络恢复还需要额外时间。
10 秒和 89 秒是不同恢复路径，不是相加后固定重启。硬件看门狗不根据视觉应用、网页或 SSH
是否可访问决定复位；软件网络重启的冷却/次数限制也不限制硬件看门狗复位。

硬件看门狗优先按官方 `watchdog_demo/test-watchDog/main.c` 选择 `dw_wdt`（本板为
`/dev/watchdog1`），由 systemd PID 1 持有。旧 GPIO 接管迁移只配置下次正常启动使用 DW，
提示 `reboot_required`，不在线执行 `daemon-reexec` 切换计时器。安装持久设置
`kernel.panic=10`，保留已有非零管理员值。不主动把普通应用异常、OOM 或警告升级为内核崩溃。

系统恢复页面显示两种整机保护的实际状态，并提供独立开关，技术信息按需展开。程序退出重启与
卡住恢复在单独的程序分类操作。保护状态取自系统，不通过修改网页状态模拟开启。

### 系统保护开关与时间设置

- “整机卡死自动重启”：保存为下次启动的 systemd 配置，不在线执行 `daemon-reexec`、关闭设备、
  停止喂狗或自动重启。保存后当前保护继续按原状态运行，页面明确显示等待正常重启生效。
- “系统崩溃自动重启”：保存 `kernel.panic` 配置并立即应用；关闭设为 0，重新开启恢复上次非零
  等待时间，首次使用默认 10 秒。只修改崩溃后的行为，不触发崩溃或立即重启。
- 系统恢复页面每 1 秒读取一次状态；没有未保存编辑时，崩溃重启开关和等待时间跟随内核
  `kernel.panic` 实际值。命令行临时修改不自动写入持久配置，页面显示与重启后设置的差异，
  可点击保存将当前选择持久化。关闭时保留已保存的非零等待时间；硬件待重启设置仍保留。
  有未保存编辑时保留编辑，外部状态变更触发版本冲突，需重新读取再保存。
- 页面直接提供三项时间设置，不需要展开技术信息：
  - **卡死复位等待时间**：1～86400 秒，对应 `RuntimeWatchdogSec`，从最后一次成功喂狗起算。
  - **重启阶段看门狗超时**：1～86400 秒，对应 `RebootWatchdogSec`，保护结束服务后的重启阶段，
    不代表整个重启流程的总时限。
  - **崩溃重启等待时间**：0～2147483647 秒，保存后立即生效。页面填 0 表示立即尝试重启，
    后台写入 `kernel.panic=-1`；停用保护需关闭独立开关，后台才写入 `kernel.panic=0`。
    已有负数配置仍保留，页面统一显示为 0（立即重启）。
- 页面将卡死、崩溃两条恢复路径分组，各自的开关与等待时间放在同一组；重启阶段超时单列为
  硬件兜底，并明确随“整机卡死自动重启”开关启用。它只在常规服务结束后的正常重启最后阶段
  使用，不覆盖之前的停止服务过程；内核 panic 重启不一定经过这一阶段。
- 三个时间不能直接相加。内核 panic 发生后若同时停止喂狗，软件崩溃重启与硬件复位可能同时
  等待，硬件也可能先触发。单独的网页失联、SSH 断开或程序卡住不能证明整机卡死或内核 panic；
  硬件看门狗只按是否继续喂狗决定复位，不据这些访问或业务现象判定故障。
- 修改硬件超时与修改硬件开关一样，等待正常重启设备后生效；只改时间也会显示待重启，
  之后保存崩溃设置不会清除该状态。设备重启后继续显示系统报告的实际超时；硬件可能按支持的
  档位调整请求值，因此设置值和实际值不必相同。开关关闭时保留时间，下次开启继续使用。
- 硬件不具备条件时禁用硬件开启操作并说明原因，仍可独立管理软件崩溃保护。已经开启的硬件
  允许保存为关闭；查看状态失败不当作保护已关闭。
- 开关设置独立存于 `/etc/rk3588-runtime/system-recovery.json`，不改变网络、应用或开机意图。
  用户保存过开关后，后续安装/升级保留选择，不自动在线切换硬件，也不重新开启已关闭的保护。
- 专用覆盖文件为 `/etc/systemd/system.conf.d/zz-rk3588-recovery-switches.conf` 与
  `/etc/sysctl.d/zz-rk3588-recovery-switches.conf`；厂商基础配置保留。相同位置存在自定义文件时拒绝
  覆盖并说明原因。写入或内核应用失败会尝试恢复本次修改前的文件和内核值，并报告回滚结果。
- 写操作要求管理员权限和读取时的版本号；并发页面不能静默覆盖彼此选择。保存不重启视觉程序。
  设备重启后若实际硬件状态仍与保存值不一致，页面显示应用失败，不一直显示等待重启。

内核阻塞升级整机重启的兼容策略仍由 `recovery.json` 的 `kernel_reboot_enabled` 独立控制，默认关闭；
不是上述硬件看门狗和内核 panic 开关。网络与程序分类已有各自的启用开关。

网络故障、内核持续阻塞和每日定时重启通过统一的软件重启协调入口，合并进行中的请求，并共享
冷却；启用的故障重启策略取较长冷却和较少的 24 小时次数。定时重启不消耗故障次数，冷却中
跳过当次。先提交正常重启；只有再次确认持续内核阻塞且正常重启超过 120 秒未完成时，才允许
一次强制升级。共享状态与额度持久保存在 `/var/lib/rk3588-reboot/state.json`，服务或设备重启
不清空额度。网络执行动作前会完整重新观察本机和目标网络状态。详见[网络恢复](network-recovery.md)。

### 不同厂商板卡的能力识别

“系统故障恢复”按本机实际证据显示保护状态和处理建议，不假定所有 RK3588 的设备编号、内核和
设备树相同。底层只读取系统状态，查询接口不会打开 `/dev/watchdog*`、启动计时器、加载模块、
修改设备树或写入启动分区。`watchdog_probe.py` 位于独立运行库中，只依赖 Python 标准库。

| 检查结果 | 页面状态与处理 |
| --- | --- |
| systemd 持有已识别的硬件设备，运行期间超时非零 | 已开启；硬件复位测试结果另行判断 |
| 驱动已编入，但设备树节点或上级节点关闭 | 设备树未开启；提示按厂商流程更新匹配设备树/启动镜像 |
| 内核配置明确缺少支持 | 缺少内核驱动；提示检查厂商内核 |
| 驱动编译为模块，尚未注册对应驱动 | 驱动模块未加载 |
| 内核注册了硬件，但没有字符设备节点 | 设备节点缺失 |
| 设备可用，但没有确认 systemd 接管 | 尚未接管；先确认是否由其他喂狗服务管理 |
| systemd 持有设备，但运行期间超时为零 | 尚未启用 |
| 只发现 softdog | 仅发现软件看门狗，不作为硬件卡死保护 |
| 驱动未知或没有足够证据定位 | 驱动需确认 / 未发现可用设备，不断言硬件不存在 |
| 权限或系统状态查询失败 | 状态未知；网页刷新失败时将原状态标为未更新 |

识别支持不同的 `watchdogN` 编号和旧式 `/dev/watchdog` 别名，不通过编号推断驱动。
`CONFIG_WATCHDOG_SYSFS=n` 不会单独被判定为缺少硬件保护；厂商可能未提供 `state`、`identity`
等查询属性。无可用硬件时才进一步检查运行设备树、`/proc/config.gz` 或 `/boot/config-<内核版本>`。
当前设备状态是动态读取；缺少硬件不会让网页无法打开，也不会阻止用户单独配置网络和程序恢复。
内核 panic 软件重启仍独立显示；它不能代替全系统卡死时的硬件复位路径。
网络恢复页面也检查独立服务及 `nmcli`、`ip`、`ping` 是否存在；缺少运行条件时说明原因并阻止新开启，
已经保存为开启的策略仍允许用户关闭，不会因为依赖缺失而无法管理。

例如 ATK 板卡的 `CONFIG_DW_WATCHDOG=y`，但 `watchdog@feaf0000/status=disabled` 且没有注册设备，
页面显示“设备树未开启”，而非“已开启”。不会从另一块板卡复制硬件复位测试通过的结论。

## 网络恢复

见[独立网络恢复说明](network-recovery.md)。支持有线/Wi-Fi，默认 ping 检测只填目标 IP，
也可检查 TCP 端口。先成功检测，再对持续异常逐级恢复原连接、网络管理服务；用户明确允许且
符合本机故障条件时才请求整机重启。网络策略默认关闭，目标由现场用户设置。

网线、供电或上游设备的永久故障不能靠重启盒子修复。局域网目标可达不能证明外网、VPN 或
入站 SSH 正常；当前没有独立 SSH 服务健康探测。

## 开机自启与应用生命周期

程序管理页的“开机自启”仍由用户独立选择。系统重启后，只有已开启自启且最后要求运行的应用
才由 `rk3588-runtime-manager.service` 启动；自启不是应用崩溃后的自动重启。用户主动停止的应用
不会因后台协调被重新启动。协调服务每 5 秒检查一次，按意图绑定上传/OTA 等服务。

默认关闭应用退出重启后，同一次系统启动内已经启动或接管过的自启目标，不因其退出反复拉起；
该记录跨协调服务重启保留。重启整机后可按自启意图重新启动。应用启动失败会退避重试。

应用仍由独立 systemd transient service 托管，保持单实例、日志跟随和正常启停能力，默认
`Restart=no`，不配置应用服务看门狗。在“程序故障恢复”分类显式开启后，按设置使用退出重启和
支持的应用服务心跳。关闭应用心跳不影响 Web 与系统守护服务自身的服务看门狗。

## 安装、配置与诊断

恢复记录和其他诊断日志均有保留上限，详见[日志保留策略与恢复记录](log-retention.md)。
恢复记录由独立服务持久保存，覆盖开机补记、服务自动重启、网络恢复和用户操作；每类只保留最新 20 条。

记录分别判断**故障触发**和**恢复方式**，两者的确认程度独立。例如 pstore 留下 panic 或
LKDTM `HARDLOCKUP` 注入日志，可以确认该故障或测试曾发生，但不等于确认最终复位来源。
多条 `HARDLOCKUP` 日志按单份来源计数，日志和 pstore 的重复副本不会相加；注入条数不证明
相同数量的不同核心都成功锁死。panic 原因提取忽略日志结尾标记，SysRq 测试独立说明。

诊断采样每分钟保存一次实际 `kernel.panic`、systemd 的运行看门狗超时、PID 1 持有的
看门狗设备和驱动，不打开看门狗设备。故障前 180 秒内的同次启动采样可以支持硬件复位推测：
硬锁死测试前硬件保护已运行，或 panic 前最近采样为 `kernel.panic=0` 且硬件保护已运行。
此时显示“有依据的推测”，并列出采样时间差、实际超时及缺失的证据；采样与故障之间可能
发生设置变化，仍不能排除人工复位或重新上电。不会用本次启动后的保护设置倒推上次故障。
采样过旧、来自另一启动周期、只有 softdog 或已关闭的保护，都不能支持此推测。

硬件 `bootstatus` 的 `WDIOF_CARDRESET` 标志支持确认看门狗复位。内核重启倒计时只证明
已安排软件重启；`reboot: Restarting system` 证明已进入软件重启入口，最终也可能卡住并由
硬件接管。本板当前内核未暴露 `bootstatus` 和复位原因接口，页面会说明这两项具体限制，
不会把所有重启都认定为看门狗复位。若需要每次明确区分软件、看门狗、外部复位和掉电，需由
匹配的 BSP/启动固件在早期保存 SoC/PMIC 复位状态，再提供给 Linux 读取。

升级判定逻辑时，只允许从仍满足新鲜度检查的残留日志补充当前启动的已有记录，保留原时间；
不会使用最新一次残留日志改写更早的启动记录。更早的 panic 记录只根据该条记录自己保存的
原始证据补充恢复判断、修正原因解析；历史缺失的保护状态和硬件复位原因不会补造。

完整部署使用 `sudo ./install.sh offline`，首次联网准备环境可用 `online`。
平台库安装在 `/usr/lib/vision-analysis-platform/python/rk3588_runtime/`，Web 旧模块保留兼容导入。
卸载 Web 不停止平台保护。升级不会替用户打开原来关闭的应用自启，也不会替用户启动停止的应用。

- `/etc/systemd/system.conf.d/90-rk3588-watchdog.conf`：硬件看门狗选择与超时。
- `/etc/sysctl.d/90-rk3588-recovery.conf`：内核 panic 自动重启。
- `/etc/rk3588-runtime/recovery.json`：兼容的运行平台策略；应用级开关默认关闭。
- `/etc/rk3588-runtime/network-recovery.json`：独立网络恢复策略。
- `APPS_ROOT/.console_runtime_state.json`：用户启停和自启意图。
- `/var/lib/rk3588-watchdog-validation/`：本机硬件复位测试记录。

```bash
./install.sh status
python3 services/framework/system_watchdog/install_watchdog.py status
systemctl status rk3588-network-recovery.service
systemctl show --property=RuntimeWatchdogUSec,RebootWatchdogUSec
cat /proc/sys/kernel/panic
```

兼容保留的 `rk3588-recovery.timer/service` 只处理特定项目线程的持续内核阻塞，需显式策略允许，
默认关闭升级重启，不属于页面中的日常配置。其作用不能等同于全系统卡死检测。

## 验证与本板复位记录

```bash
python3 -m pytest services/framework/runtime_manager/tests services/framework/system_watchdog/tests -q
python3 -m pytest web_console/frontend/tests/test_recovery_settings.py -q
```

自动与隔离服务测试不会触发整机崩溃。现场部署前还需要验证真实网络和重启后的远程可访问性，
测试过程中应有现场接管能力。软件不能修复供电、存储介质损坏或必须断电才能解除的硬件故障。

2026-10-15 本板首次整机测试未通过：当时 systemd 持有 `gpio-wdt`，喂狗 GPIO 持续翻转；
故障注入后用户等待约 5 分钟仍未自行恢复，最终人工断电开机。原始记录位于
`/var/lib/rk3588-watchdog-validation/`。这不能算硬件复位成功，也尚不足以定位 GPIO 电路的具体故障。
官方例程使用 DW，修复后优先使用相同驱动。

同日完成 DW 的独立复位验收：PID 1 持有 `/dev/watchdog1`，驱动为 `dw_wdt`，运行超时实际
返回 89 秒。测试时临时设 `kernel.panic=0` 排除软件定时重启，再以 SysRq `c` 注入内核崩溃。
记录估计约 89.7 秒后进入新内核启动，SSH、Web、NetworkManager 和独立运行守护均恢复；
开机后的 `kernel.panic` 恢复为持久配置 10。用户确认设备自行恢复，无人工断电干预。
该板本次受控内核崩溃的硬件复位验收通过，结论不扩展到网络断线、SSH 单服务卡死或其他未测故障。
89.7 秒是根据时间戳与开机 uptime 得到的估计，不是从故障到远程登录恢复的严格时限。

原始记录 `dw-reset-triggered.json`、`dw-reset-after.json` 保持原样；后者写入时尚未取得人工干预
确认，因此仍保留待确认状态。最终结论及用户确认记录在 `dw-reset-reviewed.json`、
`assessment.json`；第一次 GPIO 失败另存为 `assessment-gpio-failed.json`。以上文件位于
`/var/lib/rk3588-watchdog-validation/`，仅作为本机运维记录，其他设备需独立验收。
