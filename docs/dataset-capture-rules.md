# 数据集采集条件

Web 数据集采集复用模型检测结果，用用户配置的类别存在、缺失、数量与逻辑组合，自动筛选值得人工检查和补标的原始帧。检测结果是采集依据，不是人工确认的真实标签。

## 条件语义

规则针对同一通道、同一帧、明确选定模型的有效推理结果执行。`present(C)` 表示类别 C 达到该条件的最低置信度且数量至少为 1；`absent(C)` 表示在同样的置信度和区域约束下数量为 0。

组合操作为 ALL（并且）、ANY（或者）、NOT（取反），可嵌套。基础条件还支持数量比较（等于、不等于、大于、大于等于、小于、小于等于），每条条件可独立设置置信度。

| 用户意图 | 条件 |
| --- | --- |
| x、y、z 均出现，a、b 均缺失 | ALL(present(x), present(y), present(z), absent(a), absent(b)) |
| x 或 y 至少一类缺失 | ANY(absent(x), absent(y)) |
| x、y 都缺失 | ALL(absent(x), absent(y)) |
| x、y 至少一类出现，而 a 缺失 | ALL(ANY(present(x), present(y)), absent(a)) |
| 有人，但没有可见安全帽或未佩戴头部 | ALL(present(person), absent(helmet), absent(bare_head)) |

不存在于选定模型类别表中的名称属于配置错误；推理暂停、尚无结果、断流、推理失败与过期结果属于未知状态，均不得按“数量为零”触发缺失规则。规则阈值不得低于模型输出过滤阈值而声称仍能使用被过滤的检测框。

支持三种通用条件：类别出现/缺失与指定数量、两类目标的数量比较、逐个主体的空间关联。
“有人但整幅图没有帽子”与“至少一个人没有匹配到帽子”是两种不同条件。

### 两类数量比较

```json
{"compare_counts": {
  "left": {"class": "x", "min_confidence": 0.3},
  "right": {"class": "y", "min_confidence": 0.3},
  "op": ">"
}}
```

支持 `==、!=、>、>=、<、<=`。例如 x 检测到 2 个、y 检测到 1 个时，上述条件成立。
两类都按同一计数 ROI 筛选，置信度可分别设置。数量比较不判断空间对应关系。

### 逐个主体检查关联

```json
{"association": {
  "subject": {"class": "x", "min_confidence": 0.3},
  "object": {"class": "y", "min_confidence": 0.3},
  "relation": "center_inside",
  "state": "unmatched",
  "quantifier": "any",
  "one_to_one": true,
  "min_overlap": 0.5,
  "max_distance": 1
}}
```

类别来自用户的模型标签，没有固定业务类别。上述配置表示“至少一个 x 没有匹配到对应的 y”。
两个 x 只有一个对应的 y 时采集；即使 y 数量足够，但某个 x 的对应位置没有 y，也可采集。

一个主体可关联多个类别。页面点击“添加关联类别”，填写安全帽和裸露头的模型类别名，然后选择
“至少一个”主体、“以下类别都没匹配到”。对应配置用 `objects` 替代 `object`：

```json
{"association": {
  "subject": {"class": "person", "min_confidence": 0.3},
  "objects": [
    {"class": "helmet", "min_confidence": 0.3},
    {"class": "bare_head", "min_confidence": 0.5}
  ],
  "relation": "center_inside",
  "state": "unmatched",
  "quantifier": "any",
  "one_to_one": true
}}
```

这些类别构成同一个匹配候选池：对同一个主体，匹配到任意一类就算成功，只有所填类别全部没有
匹配到才算缺失。如果两个人分别匹配到安全帽和裸露头，不采集；如果这两类目标都在第一个人框内、
第二个人没有任何对应目标，则采集。`state=matched` 则表示匹配到了其中任意一类。
允许 1 至 32 个不同的关联类别，每类独立设置置信度；不能同时填写 `object` 和 `objects`。
原来的单类别 `object` 配置继续有效。新增多个类别后需要使用支持 `objects` 的新版视觉程序，
仅更新 Web 页面不能让旧引擎识别新规则。

- `relation=center_inside`：y 框中心位于 x 框内。
- `relation=subject_center_inside`：x 框中心位于 y 框内。
- `relation=overlap`：框交集面积占 y 框面积达到 `min_overlap`（大于 0、最多 1，默认 0.5）。
- `relation=subject_overlap`：框交集面积占 x 框面积达到 `min_overlap`，用于逐个检查小主体是否在大关联框中。
- `relation=near`：两框中心距离不超过 x 框对角线乘 `max_distance`（大于 0、最多 100，默认 1）。
- `state=unmatched/matched`：判断没有匹配到/匹配到了对应目标。
- `quantifier=any/all/count`：至少一个/全部/按数量判断的主体满足该状态。`count` 模式需要
  `"count":{"op":">=","value":2}` 等数量要求。没有有效主体时关联条件不成立，包括“全部”模式。
- 默认 `one_to_one=true`，每个关联目标最多分配给一个 x，多类别共用同一个匹配池，通过最大二分匹配避免贪心分配的假缺失。
  设置 false 允许同一个 y 为多个 x 提供关联。相同类别关联不会用一个框匹配它自己。
- ROI 只筛选关联主体 x；关联目标 y 来自同帧模型的全部有效输出，允许位于计数 ROI 外。
  推理 ROI 之外的目标不会凭空补出。关联只使用有效矩形框，各类别的置信度分别过滤。

包含关系有方向，交换主体和关联类别不会自动反转方向。页面的匹配选项、方向说明和任务卡片会直接显示实际类别名。例如，主体为 `helmet`、关联类别为 `person` 时，原有 `overlap` 表示“person 至少 50% 的面积在 helmet 框内”；要找对应人框漏检，应选择 `subject_overlap`，即“helmet 至少 50% 的面积在 person 框内”，或选择 `subject_center_inside` 判断帽子中心是否在人框内。

逐顶查找没有对应人框的安全帽，可使用：

```json
{"association": {
  "subject": {"class": "helmet", "min_confidence": 0.3},
  "object": {"class": "person", "min_confidence": 0.3},
  "relation": "subject_overlap",
  "min_overlap": 0.5,
  "state": "unmatched",
  "quantifier": "any",
  "one_to_one": false
}}
```

正常戴帽且帽子落在人框内时不命中；两顶帽子中有一顶没有对应人框时命中，即使画面中仍有其他人框。关闭一对一分配允许一个人框对应多个帽子框，避免仅因分配不足而触发。命中表示没有找到符合阈值与空间关系的人框，也可能来自帽子误报，需要查看采集原图确认。已有任务保留原有判断含义，编辑并保存新的匹配方向后才生效。

数量比较和关联条件均可放进 ALL、ANY、NOT 组合。不同关联条件各自匹配；例如两条“至少一个 x
缺少 y/z”的 AND，可能由不同 x 分别满足，并不表示同一个 x 同时缺少 y 和 z。
空间关联是模型检测框的几何判断，不证明真实佩戴/归属关系，也不判断头部是否可见。

### 逐个主体检查关联目标数量

抓“一个人匹配到两个安全帽”的可疑帧时，选择“逐个目标检查关联”，主体为 `person`，关联类别为
`helmet`，主体数量要求为“至少一个”，抓图情况选“按每个主体的关联目标数量判断”，数量选“超过 1 个”。
空间方式选择“helmet 的中心在 person 框内”，会统计整个人框内的帽子检测框，包括裤子上的帽子误报。

```json
{"association": {
  "subject": {"class": "person", "min_confidence": 0.3},
  "object": {"class": "helmet", "min_confidence": 0.3},
  "relation": "center_inside",
  "state": "count",
  "object_count": {"op": ">", "value": 1},
  "quantifier": "any"
}}
```

`object_count` 判断每个主体范围内的关联框数量，支持 `==、!=、>、>=、<、<=`，数量为 0 至 10000
的整数；只在 `state=count` 时填写。`quantifier` 仍然判断有多少个主体满足上述条件，比如
`quantifier=count` 加 `count={"op":">=","value":2}` 表示“至少两个人，各自范围内的帽子数量超过 1”。
两种数量分别配置，不能用整幅图的帽子总数替代逐人的统计。

数量模式统计全部符合置信度与空间关系的候选框，每个检测框计一次，多个关联类别合计；不使用
一对一分配，也不能填写 `one_to_one`。如果两个主体框重叠，同一个关联框可能计入两人的范围。
没有有效主体时仍不触发采集。原来的匹配成功/缺失模式保持一对一匹配的语义。

两个人各一个帽子时不采集；两个人、两个帽子但两个帽子都在第一个人身上时采集。
头部真帽与裤子误报都位于同一个人框内时也会采集。这只是数量异常的候选帧，实际原因可能是误报、
重复检测或手持帽子，仍需人工检查。它不能识别“只有裤子误报一个帽子”且数量正常的情况。
点击“添加另一种抓图情况”，可同时保留“安全帽和裸露头都缺失”的规则，任意一种命中都采集。
新增数量模式需要更新视觉程序并重新启动才能使用。

## 配置入口与触发节奏

在 Web 侧边栏打开“数据集采集”，点击“新建采集任务”，选择采集通道、确认模型类别，再填写规则。无需更换通道业务逻辑或新建推理通道。同一任务的多组规则之间使用“或”，一帧命中多组规则只采集一次。

页面自动管理规则名称，不需要填写条件组备注。“再加一条必须满足的条件”要求当前条件和新条件同时满足；“改成不满足当前条件时抓图”把当前条件作为整体检查，例如将“检测到 person”改为“没检测到 person”。按钮旁会显示修改后的抓图条件。“添加另一种抓图情况”则是增加一组可独立触发抓图的条件，满足任意一组即可。

“抓图间隔”限制相邻采样的频率；“持续确认时间”要求条件连续成立后再触发。“每次刚满足时抓一次”按条件从不成立变为成立触发，仍遵守抓图间隔。过期、重复或无效推理结果不会重复触发采集。

图片由电脑接收程序保存到用户选择的目录，任务管理和当前存图统计均在 Web 页面查看。操作与部署说明见[电脑数据集采集](computer-dataset-collection.md)。
