# RK3588 视觉算法引擎设计评审

> 评审基线：2026-07-30 当前工作区。本文区分“已经形成的稳定边界”和“仍值得继续改进的事项”。

## 一、总体结论

当前框架已经符合“可复用视觉算法引擎”的基本定位：

- channel logic 只实现识别结果到业务事件的判断，不感知 HTTP、Dify、地址或密钥；
- `report_event()` 把事件、来源和自定义字段写成稳定的本地事件；
- report policy 选择连接 Profile 与接口契约并保存媒体快照；
- Python 发件箱只负责状态、重试和调度，adapter 负责具体远端协议；
- Web 根据 adapter catalog 动态生成连接配置；接口契约编辑器从当前 logic 清单动态生成字段
  选择器，并支持保存、预览请求和测试发送；
- 图片和视频共用 `requested/generating/ready/failed` 状态模型；
- 不保留旧上报接口或旧配置的兼容分支。

新增检测功能通常只需新增 logic 模块；远端接口字段变化通常只需修改一个接口契约；新增一类
协议时新增 adapter 和 catalog 声明，不需要修改算法 logic 或 C++ 事件模型。

## 二、稳定架构边界

```text
检测结果
  → channel logic
  → EventRequest(event_type, message, fields)
  → report_event()
  → event_store/<event_id>/
  → EventOutboxForwarder
  → adapter(profile, contract)
  → 远端接口
```

各层职责如下：

| 层 | 负责 | 不负责 |
|---|---|---|
| logic | 触发条件、跨帧状态、业务字段 | URL、鉴权、JSON 协议、上传 |
| C++ event | 事件建档、合并、媒体请求、容量控制 | 远端类型和字段名称 |
| report policy | 事件过滤、选择 Profile/contract、保存 C++ 所需媒体快照 | 远端字段编辑、密钥和网络执行 |
| contract | 请求方式、媒体、固定值、source→target mapping、成功条件 | 地址、密钥、算法变量求值 |
| outbox | 媒体等待、状态迁移、重试、adapter 调度 | 拼装某个业务协议 |
| adapter | 请求构造、发送、响应成功判定 | 算法触发逻辑 |
| Profile | 地址、Header、密钥、超时、通用连接选项 | 每类事件的业务字段 |

该边界应作为后续开发的硬约束。

## 三、已解决的主要问题

### 3.1 事件状态所有权

事件目录按写入者拆分：

- `event.json`：C++ 创建后只读；
- `media_state.json`：C++ 图片和录像模块维护；
- `delivery_state.json`：Python 投递服务维护；
- `delivery_retry.request.json`：Web 写请求，Python 消费。

这避免多个进程共同读改写同一状态文件。

### 3.2 协议硬编码

服务器固定 JSON 和 Dify 特判已经移出发件箱。`http_json` 与 `dify_workflow` 都通过统一
adapter 接收标准事件、连接 Profile 和接口契约。字段增删、改名、嵌套路径、固定值、类型转换、
Base64、文件上传和成功条件均由版本化契约表达。

### 3.3 结构化返回与媒体终态

`report_event()` 返回 `EventReportResult`，调用者可区分创建、合并、禁用、无投递、请求错误、
存储错误和媒体立即失败。媒体不再只有“存在/不存在”，而是显式记录生成过程和失败原因，避免
上传服务永久等待。

### 3.4 开发与测试入口

Web report 节点可以使用样例事件或本地真实事件预览最终请求，也可以执行测试发送。adapter
还可通过 `delivery_tool.py` 独立验证，因此调试远端接口不需要反复触发模型。

## 四、仍需改进的事项

### 4.1 成功投递历史

所有 delivery 成功后，事件目录会被删除。Web 当前页面因此是“待处理/失败记录”，不是成功历史。
建议增加轻量 SQLite 或 JSONL 账本，只保存事件摘要、完成时间、远端响应摘要和媒体哈希。

### 4.2 容量回收审计

发件箱达到容量或磁盘水位时需要回收旧事件，但目前缺少独立的 eviction ledger。建议记录被丢弃
事件的 ID、原因、大小和时间，并在 Web 显示容量水位、最老待发时间和累计丢弃数。

### 4.3 媒体生成超时

正常编码失败已能进入 `failed`；如果进程异常退出或编码器卡住，状态仍可能停在 `generating`。
建议由上传服务根据事件年龄和媒体 deadline 做兜底失败判定。

### 4.4 服务配置热生效

上传服务启动时读取 `config.yaml`。Web 保存 Profile 后应提供明确的“尚未应用”状态和一键重启，
或让服务监听配置变化并在校验成功后原子替换配置。

### 4.5 契约 Schema 与编辑体验

adapter catalog 已驱动 Web 表单，但仍可增强：

- 为 Profile 与 contract 增加机器可执行 JSON Schema；
- 保存前验证 contract 的 source、target、transform、固定值和媒体能力；
- 对远端响应提取结果定义统一结构；
- 增加 graph → config → graph 往返测试。

### 4.6 logic 跨帧状态易用性

`std::shared_ptr<void> *state` 的生命周期设计有效，但业务代码需要手动二次解引用和类型转换。
可在 `ChannelContext` 增加模板辅助函数：

```cpp
template<class T, class... Args>
T &state_or_create(Args&&... args);

template<class T>
T *state_if();
```

框架内部仍可保存类型擦除的智能指针，logic 不再重复样板代码；调试构建还可记录类型信息以尽早
发现错误转换。

## 五、新功能设计检查表

修改框架前依次确认：

1. 这是算法触发条件，还是远端协议变化？
2. 能否只通过 logic fields、接口契约或 Profile 完成？
3. 新能力是否应实现为 adapter，而不是加入发件箱分支？
4. C++ 是否仍只依赖稳定的事件和媒体概念？
5. Web 是否能从 catalog 得知能力，而不是按 adapter 名硬编码？
6. 是否有预览、单元测试和失败状态可验证？
7. 是否无意引入第二套旧接口、默认连接或隐式兼容路径？

只有真正跨所有业务复用的能力才应进入引擎底层。
