# 网络失联自动恢复

Web 入口为侧边栏“故障恢复 → 网络故障恢复”，支持有线、Wi-Fi，以及电脑、其他盒子或服务器
作为检测目标。默认使用 ping，只需填写设备 IP；也可选择 TCP 服务端口检测。实际执行者是独立的
`rk3588-network-recovery.service`，从系统平台库加载，只依赖
Python 标准库和系统网络工具，不导入 Web。停止或卸载 Web 不停止巡检。

## 启用

使用根安装器部署，或只安装平台：

```bash
sudo python3 services/framework/runtime_manager/install_runtime.py
```

服务默认启用并运行，网络恢复策略默认关闭；关闭时不执行网络探测和网络操作。开启策略需要
本机有 `nmcli`（NetworkManager）、`ip`（iproute2）、`ping`。保存网络策略需要 root、sudo 或
wheel 管理员权限，状态查看受现有登录保护。

1. 填写“网络检测目标地址”，例如另一台盒子或电脑的 IP `192.168.1.20`。默认“仅检测设备（ping）”
   不需要网页或其他监听服务，也不填写端口；目标设备必须保持在线并允许 ICMP Echo 回复。
   若设备不允许 ping，可选择“检测服务端口（TCP）”，填写实际开放的端口，例如 HTTPS 的 443。
   不内置公共互联网目标。局域网目标仅证明盒子到该目标的连通性，不证明外网或入站 SSH 正常。
2. 开启“网络失联自动恢复”，按现场需要选择“必要时允许重启盒子”，然后保存。整机重启默认关闭，
   不受系统故障恢复中“内核阻塞升级重启”的另一开关控制。
3. 等待首次成功连接。首次从未成功、目标改变或切换网卡时，成功前不
   执行自动恢复。相同配置、相同网卡的基线在守护或系统重启后保留。

页面默认折叠“高级设置”，其中包含指定网卡、备用目标、网络服务恢复开关、各级等待及限频。
展开或保存基础设置不会将已有自定义参数恢复为默认值。策略下一轮巡检生效，不需要重启 Web。

自动模式选择系统管理的有线/Wi-Fi 网卡中的默认路由，优先 IPv4，并在同一地址族中按 metric
排序；默认路由丢失时继续使用此前记住的网卡。双网卡或专用摄像头网络可在高级设置中显式
选择管理网卡。未由 NetworkManager 管理的接口不作为自动恢复对象。主要和备用目标合计
最多 4 个，可以混合 ping 与 TCP；任意目标检测成功即认为网络可达。

## 判断与恢复

每 15 秒巡检，开机前 120 秒等待网络建立。ping 与 TCP 探测均绑定所选网卡。ping 发送一个
ICMP Echo 请求，等待回复，总子进程超时为 3 秒；不需要目标端运行应用服务。TCP 的 DNS 与
连接在总超时 6 秒的子进程内执行，避免解析卡住拖死守护。TCP 探测只建立并关闭连接，不发送
业务请求，也不验证目标应用层是否健康。目标关闭、防火墙禁止 ping 或丢包均可能导致检测失败，
需先成功检测并结合本机网络状态判断，不能将一次无回复直接认定为盒子卡死。

| 情况 | 行为 |
| --- | --- |
| 任意目标 ping 回复或 TCP 连接成功 | 健康，清除本轮故障计时，保留限频历史 |
| 尚无首次成功基线 | 等待用户确认地址、端口及连通性，不执行自动操作 |
| 有线接口无链路信号 | 等待网线、交换机恢复，不因此恢复网络或重启 |
| 网关可达且本机地址、路由、网络服务正常，仅管理端失联 | 暂按上游异常处理，不因此重启 |
| 网络配置事务进行中、锁被占用或事务文件损坏 | 暂停并清除故障计时，避开网页切换和回滚 |
| 其他已建立基线的持续失联 | 确认期限后重新激活已知 UUID 的原连接，不新建连接 |
| 仍未恢复且允许恢复网络服务 | 等待与冷却满足后重启 NetworkManager，可能短暂影响其他网口 |
| 仍持续失联、允许整机重启且有本机异常迹象 | 超过期限并满足持久限频后请求普通系统重启 |

整机升级还要求网络服务不响应、地址缺失、路由缺失，或此前可达的同一网关现在不可达等迹象。
仅管理端不可达且网关状态未知，不足以授权整机重启。网关断电和盒子接口故障可能表现相同，
因此必须保留限频。该监控检查盒子主动访问管理端的能力，不能证明外部入站 SSH 可达，不能
修复网线、上游路由器或硬件永久故障。

恢复使用已有连接 UUID 和指定网卡，不删除连接，不修改静态 IP、Wi-Fi 密码、DNS 或持久连接
配置，不用 `nmcli device connect` 创建默认网络。每次操作前在网络事务锁和恢复协调锁内重新读取
完整状态（网卡、连接 UUID、IP、路由、NetworkManager、网关和检测目标），丢弃第一次的暂定
动作及计数，用最新状态重新决策。管理网卡或连接改变时取消动作并重新建立探测基线；异常解除、
上游故障、策略改变或读取失败时不执行旧动作，也不消耗额度。已提交给系统的操作不能通过关闭策略撤销。

## 默认参数与限频

| 参数 | 默认值 | 可设范围 |
| --- | --- | --- |
| 持续异常确认 | 180 秒 | 60～1800 秒 |
| 每级恢复后等待 | 60 秒 | 30～600 秒 |
| 网络操作最小间隔 | 300 秒 | 60～3600 秒 |
| 持续异常整机重启期限 | 900 秒 | 300～7200 秒 |
| 整机重启最小间隔 | 3600 秒 | 1800～86400 秒 |
| 24 小时最多网络故障重启 | 2 次 | 1～5 次 |

每小时最多 6 次网络恢复操作，同时受每级等待和最小间隔约束。一轮最多重新激活连接、恢复
网络服务各一次；未恢复时，距上次操作至少 15 分钟且满足冷却后再试一轮。整机期限必须留出
连接和网络服务两级等待时间。

网络升级重启、内核阻塞升级重启和每日定时重启共用平台 `reboot_coordinator`。相同启动周期内
已有请求时合并原因，不重复提交或计数；网络修复持有同一协调锁，定时重启最多等待 60 秒，
不会直接打断正在执行的恢复动作。不同故障恢复策略同时允许整机重启时，共享冷却取较长值，
共享 24 小时故障次数上限取较小值。定时重启也遵守共享冷却，但不占故障次数额度；冷却中
跳过当次定时任务，并记录原因，不追补执行。

所有软件入口先请求正常重启。只有内核阻塞监测再次确认持续阻塞、程序恢复仍失败，且已有正常
重启请求超过 120 秒时，才允许升级一次强制重启；升级沿用原请求及计数。正常重启提交后
300 秒系统仍为运行或降级状态时，可以释放待重启状态，但不清空冷却和次数。硬件看门狗与
内核 panic 保持独立，不受软件协调额度限制。

操作及重启请求在执行前通过文件和目录 fsync 持久保存，守护和整机重启不清空额度。时钟回拨
时保留未来时间戳，保守维持冷却。状态损坏会停止操作，而非清空次数后继续重启。同一时间只
允许一个守护或命令行单轮检查持有实例锁。

共享记录位于 `/var/lib/rk3588-reboot/state.json`，通过进程锁和文件、目录 fsync 持久保存，
首次请求会导入旧网络/内核恢复记录中的近 24 小时重启次数，升级不重置额度。新系统启动仅清除
旧启动周期的待重启标记。共享记录异常时停止自动动作，不通过清空文件继续重启。

## 配置、状态与接口

- `/etc/rk3588-runtime/network-recovery.json`：网络策略，与应用恢复策略分开保存。
- `/run/rk3588-network-recovery/status.json`：本次启动的巡检状态。
- `/var/lib/rk3588-network-recovery/state.json`：成功基线、连接 UUID、限频和最近 20 条兼容事件。
- `/var/lib/rk3588-runtime/recovery-history.json`：包含原因、动作及实际结果的循环恢复记录，每类最新 20 条，详见[日志保留策略](log-retention.md)。
- `APPS_ROOT/.network_transactions/.lock`：与 Web 网络设置共用；自定义 `NETWORK_TRANSACTION_DIR`
  时，Web 和系统服务必须使用同一目录。
- `GET /api/system/recovery/network`：策略、版本、服务、网卡、探测结果和最近 20 条记录。
- `PUT /api/system/recovery/network`：管理员提交 `{policy, revision}`，版本冲突返回 409。

目标格式：ping 为 `{"host": "192.168.1.20", "method": "ping"}`；TCP 为
`{"host": "192.168.1.30", "port": 8080}`。旧版省略 `method` 的 TCP 配置保持原有格式与策略
版本，不因软件升级丢失成功检测记录；主动更改检测方式后必须重新成功检测。

```bash
systemctl status rk3588-network-recovery.service
cat /run/rk3588-network-recovery/status.json
journalctl -u rk3588-network-recovery.service -b
```

`python3 -m rk3588_runtime.network_recovery --once` 执行真实巡检，可能恢复网络或请求重启，
不能与已运行的守护并发执行；它不是只读诊断命令。

平台安装和 Debian/Ubuntu 离线平台包均包含本服务。卸载控制台保留它，卸载整个平台停止它。
服务使用 systemd 120 秒服务看门狗和退出重启，不占用硬件看门狗、不改变已验收的 DW 配置。

## 验证

```bash
python3 -m pytest services/framework/runtime_manager/tests services/framework/system_watchdog/tests -q
RK3588_SYSTEMD_TESTS=1 python3 -m pytest services/framework/runtime_manager/tests/test_network_systemd_integration.py -q
```

测试覆盖基线、路由切换、有线与 Wi-Fi、上游故障、拔线、事务互斥、分级恢复、持久限频、时钟
回拨和禁用竞态。systemd 测试以隔离平台和模拟网络命令验证真实进程边界，不切断当前管理网卡
或重启盒子。真实网络恢复应在有现场接管能力的维护窗口另行验收。

前端构建后，可用 `python3 -m pytest web_console/frontend/tests/test_recovery_settings.py -q`
验证基础设置保存、隐藏参数保留、分类切换草稿与高级参数校验；需 Playwright 和 Chromium，
浏览器仅访问隔离测试服务，不修改设备策略。

命令语义见 [NetworkManager nmcli 文档](https://networkmanager.dev/docs/api/latest/nmcli.html)。
