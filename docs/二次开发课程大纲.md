# RK3588 上层通道逻辑二次开发课程大纲

> 课程定位：教开发者在 `logic_xxx` 业务模块中使用系统已经提供的视频帧、模型结果、区域、时间和通道信息，完成自己的判断、绘制、Web 参数、Web 按钮和事件上报。  
> 本课程不展开视频解码、NPU 推理实现、线程调度、Web 前端内部代码和上传服务内部实现。  
> 适用代码基线：本仓库当前源码，核对日期为 2026-07-30。
>
> 使用说明：本文以逐步创建 `logic_course_person_dwell` 和 `logic_course_motion_cv` 作为完整课程项目，这两个名称是学员要创建的产物，不是当前内置模块。仓库中的 `logic_course_01` ～ `logic_course_07` 是可直接运行的分课示例；`logic_course_08` ～ `logic_course_10` 当前仍是开发中的任务骨架，不能当作完成答案。

## 一、这门课要解决什么问题

完成课程后，开发者应能独立回答并完成下面这些事情：

1. 我想增加一种业务规则，应该新建哪些文件？
2. 我怎样取得当前视频帧、模型检测结果、ROI（Web 上画出的关注区域）、时间、FPS 和通道号？
3. 我怎样读取 YOLO 已经输出的类别、置信度和目标框，并增加停留时间、冷却时间、显示开关等自己的业务参数？
4. 为什么增加普通参数后，Web 可以自动显示输入框、开关或下拉框？
5. 怎样让同一个逻辑被多个通道使用，但各通道的计时和状态互不影响？
6. 怎样通过 Web 按钮复位状态或手动生成一次测试事件？
7. 怎样把业务字段、告警图片和事件视频交给系统上报？
8. 怎样在不修改框架中央代码和 Web 字段列表的情况下，新增或删除一个普通业务模块？

### 1.1 课程只关注上层业务开发

| 重点学习 | 只需知道结果，不展开内部实现 |
|---|---|
| 编写 `logic.cpp` 中的业务判断 | 视频如何解码、缩放和送入模型 |
| 编写 `logic.json` 中的参数、按钮和上报字段 | NPU、RGA、跟踪器内部算法 |
| 使用 `ChannelContext` 取得系统数据 | 线程、锁和运行快照如何实现 |
| 处理模型结果或直接使用视频帧 | CMake 如何扫描所有源码的内部过程 |
| ROI、计时、去重、绘制和状态保存 | React Flow 如何把画布转成 JSON |
| Web 参数、按钮、上报节点和接口契约选择 | HTTP 重试、视频编码和上传服务内部代码 |
| 验证模块是否独立、是否可以删除 | systemd、OTA 和完整运维体系 |

遇到上述底层内容时，教师只说明“系统已经提供了什么”和“业务代码怎样使用”，不要求学员修改底层源码。

### 1.2 一条通道的业务关系

```text
视频流
  ├─ 推理开启：视频帧 -> 模型结果 -> 可选的 logic 后处理
  └─ 推理关闭：视频帧 ------------> 可选的 logic 传统计算机视觉（CV）处理

logic 可以做：业务判断、保存状态、绘制、创建上报事件
Web 可以做：选择 logic、填写参数、画 ROI、点击按钮、配置上报去向
```

`logic` 是可选步骤。某个通道没有配置 `logic` 时，系统仍会显示视频，并按模型配置绘制检测结果，只是不执行额外的业务后处理。

### 1.3 本课程的最终产物

课程不再要求每节课创建一个只能用于演示的探针模块，而是逐步完成两个普通业务模块：

```text
vision_analysis/src/logic/modules/
├── logic_course_person_dwell/
│   ├── logic.cpp       # 处理模型结果：人员在区域内停留后上报
│   └── logic.json      # 参数、Web 按钮和上报字段
└── logic_course_motion_cv/
    ├── logic.cpp       # 处理视频帧：传统帧差运动检测
    └── logic.json      # 运动阈值等参数
```

还应得到：

- 一份可由 Web 保存并重新打开的课程配置；
- 一份课程验收记录，包含每课要求的截图、操作结果和问题记录；
- 至少一条从业务触发到本地事件、再到远端投递结果的完整记录。

`logic_course_person_dwell` 是贯穿课程的主项目。`logic_course_motion_cv` 用来证明业务模块不依赖模型结果，也可以直接处理视频帧。

## 二、开始写代码前，先分清四类内容

这是整门课程最重要的基础。新手最容易把模型结果、模型设置、logic 参数和运行状态都当成一类“配置参数”，最后造成重复设置。

| 数据类别 | 例子 | 在哪里取得或保存 |
|---|---|---|
| 系统已经提供的数据 | 通道号、当前帧、ROI、时间、FPS，以及 YOLO 输出的类别、置信度、目标框和跟踪编号 | 从 `ctx` 和 `ctx->results` 读取 |
| 模型节点的设置 | 模型文件、`detect_classes`、`obj_thresh`、`nms_thresh` | 在 Web 模型节点中配置，模型先按这些条件生成结果 |
| 自己定义的业务参数 | ROI 名称、停留秒数、冷却时间、显示开关、告警文案 | 在本模块 `logic.json` 声明，用 `ctx->param_*()` 读取 |
| 运行中会变化的状态 | 已停留多久、是否已经报警、上次报警时间、按钮是否待处理 | 保存在本通道的 `ctx->state` 中 |

简单判断方法：

- YOLO 已经输出的 `label`、`score`、`box` 和 `track_id`，直接从结果中读取；
- 模型应输出哪些类别、最低推理置信度是多少，优先在 Web 模型节点中配置；
- 系统或模型本来就提供的内容，不要再定义一份同名 logic 参数；
- 希望用户在 Web 中填写的业务规则，放进 `logic.json`；
- 随着每一帧不断变化的值，放进 `ctx->state`，不要写进配置；
- 多个通道会共用同一段 logic 代码，但参数和 `ctx->state` 是各通道独立的。

例如，模型节点配置 `detect_classes=["person"]`、`obj_thresh=0.5` 后，logic 收到的人员结果已经通过模型的最低置信度筛选。logic 只需要读取每个结果的 `label` 和 `score`，不必再声明同义的 `target_label` 和 `score_threshold`。

只有业务确实需要第二层筛选时才增加 logic 参数。例如模型为了画面展示保留 `score >= 0.3` 的结果，但“人员停留报警”只允许 `score >= 0.7`，这时可以增加一个名称明确的 `alarm_score_threshold`。它代表报警规则，不是 YOLO 原始置信度。

### 2.1 常用的系统数据

| 想取得的内容 | 推荐写法 | 新手需要注意的地方 |
|---|---|---|
| 通道号 | `ctx->chnId` | 与配置中的 `channels[].id` 是同一个值 |
| 当前视频帧 | `ctx->frame` | 先判断是否为空；它是 BGR 图像 |
| 当前帧编号 | `ctx->frame_id` | 可用于显示和问题定位 |
| 计算时间间隔 | `ctx->timestamp_ms` 或 `ctx->dt_ms` | `timestamp_ms` 适合计时，不是日历时间 |
| 当前真实时间 | `ctx->time_hms()`、`ctx->time_str()` | 适合显示或写入上报字段 |
| 是否启用推理 | `ctx->infer_enabled` | 关闭推理时，`results` 通常为空，但 logic 仍可处理帧 |
| 推理/显示 FPS | `ctx->infer_fps`、`ctx->disp_fps` | 用于状态显示，不要复制成自定义参数 |
| 模型结果 | `ctx->results` | 先判空，再遍历其中的 `AlgoResult` |
| 结果类别 | `result.label` | YOLO 根据 `labels.txt` 给出的类别，不是 logic 参数 |
| 结果置信度 | `result.score` | YOLO 对这个结果给出的分数，不是 logic 参数 |
| 结果目标框 | `result.box` | 已与运行时 ROI 放在同一坐标范围内 |
| 结果跟踪编号 | `result.track_id` | 跟踪器提供；小于 0 时不能当作可靠目标身份 |
| ROI | `ctx->roi_count()`、`roi_find()`、`roi_contains()` | ROI 与检测框已经在同一坐标范围内 |

完整字段不要求背诵，需要时查阅 [ChannelContext API 参考](skills/rk3588-channel-logic/references/channelcontext-api.md)。

### 2.2 自定义参数与 C++ 读取方法

| `logic.json` 中的类型 | C++ 中的读取方法 | 适合的例子 |
|---|---|---|
| `number` | `ctx->param_float("key")` | 停留秒数、冷却秒数 |
| `integer` | `ctx->param_int("key")` | 最大人数、间隔次数 |
| `boolean` | `ctx->param_bool("key")` | 是否显示文字、是否启用某规则 |
| `string` | `ctx->param_string("key")` | ROI 名称、告警文案、工作模式 |
| `array` / `object` | `ctx->param_json("key")` | 少量结构化规则；业务代码还要检查内部内容 |

普通业务参数只修改当前模块的 `logic.cpp` 和 `logic.json`。不要为了一个新参数去修改 `ChannelConfig`、Web 字段列表或打包后生成的 `logics.json`。

### 2.3 `logic.json` 怎样连接 C++ 和 Web

```text
logic.json.parameters
  -> Web 自动生成参数控件
  -> 用户保存每个通道的参数值
  -> logic.cpp 用 ctx->param_*() 读取

logic.json.actions
  -> Web 自动生成通道操作按钮
  -> logic.cpp 的按钮处理函数接收动作

logic.json.report_fields
  -> Web 显示可供上报映射的业务字段
  -> logic.cpp 上报同名字段和值
```

普通模块不需要写专用 Web 页面。`logic_path_sop` 因为有专用 SOP 画布，是当前的特殊模块，
不作为普通 logic 的开发模板；但它和普通模块一样只通过 `logic_parameters` 保存业务配置。

Web 保存某个通道的普通业务参数时，实际会把值放在这个通道的 `logic_parameters` 中。学员通常通过 Web 修改，不需要手写整份运行配置：

```json
{
  "logic": "logic_course_person_dwell",
  "logic_parameters": {
    "roi_name": "work_area",
    "dwell_sec": 5,
    "show_overlay": true,
    "alarm_message": "人员在区域内停留超时"
  }
}
```

## 四、每节课的内容与明确产出

### L0 · 认识上层 logic 的输入和输出

#### 本节目标

先建立正确概念：logic 是视频或模型之后的可选业务处理步骤，不是模型本身，也不是上传服务。

#### 学习与操作

1. 在 Web 中配置一个视频流和模型，但不选择任何 logic；确认视频和模型框仍正常显示。
2. 给同一通道选择 `logic_course_07`；确认画面出现该模块自己的数字。
3. 观察一个 logic 可以接收什么：帧、模型结果、ROI、时间、参数和按钮动作。
4. 观察一个 logic 可以输出什么：状态文字、图形、业务事件和业务字段。
5. 了解推理关闭后仍可配置 logic，并直接使用视频帧做传统 CV。

#### 本节产出

- [ ] 一张“未选择 logic，但视频和模型框正常显示”的截图；
- [ ] 一张“选择 `logic_course_07` 后出现业务叠加”的截图；
- [ ] 一张不超过一页的输入/输出关系图；
- [ ] 在课程验收记录中，用自己的话写出模型、logic、Web 上报配置三者各负责什么。

#### 通过标准

学员能说明：不配置后处理逻辑时系统做什么；推理模式和传统 CV 模式分别从哪里取得输入。

### L1 · 创建第一个普通业务模块

#### 本节目标

创建 `logic_course_person_dwell`，先让它被系统发现并在画面上显示一行文字。

#### 学习与操作

新建目录：

```text
vision_analysis/src/logic/modules/logic_course_person_dwell/
├── logic.cpp
└── logic.json
```

最小 C++ 入口：

```cpp
#include "logic/core/logic_common.h"

static void logic_course_person_dwell(ChannelContext *ctx)
{
    if (!ctx || !ctx->frame || ctx->frame->empty())
        return;

    draw_text(ctx, "course logic running", cv::Point(20, 30));
}

REGISTER_LOGIC(logic_course_person_dwell);
```

最小 `logic.json`：

```json
{
  "label": "课程：人员停留告警",
  "parameters": {
    "type": "object",
    "additionalProperties": false,
    "properties": {}
  },
  "report_fields": []
}
```

`REGISTER_LOGIC()` 只传入入口函数，函数名会自动成为 Web 和配置使用的 logic ID。源 `logic.json` 不写 `name`；列表顺序没有业务意义，也不需要 `_order` 字段。

#### 本节产出

- [ ] `logic_course_person_dwell/logic.cpp`；
- [ ] `logic_course_person_dwell/logic.json`；
- [ ] 清单检查通过的记录；
- [ ] `--list-logics` 中出现新模块的记录；
- [ ] Web 选择该模块后，画面显示 `course logic running` 的截图。

#### 通过标准

新增模块时只创建本模块目录，没有修改中央注册表、其他业务模块或 Web 内置逻辑列表。

### L2 · 在逻辑函数中读取系统数据

#### 本节目标

学会使用 `ctx`，不用自己重复定义系统已经提供的数据。

#### 学习与操作

在主项目画面上显示：

- `ctx->chnId`：当前通道；
- `ctx->frame_id`：当前帧号；
- `ctx->time_hms()`：当前时间；
- `ctx->infer_enabled`：推理是否开启；
- `ctx->infer_fps` 和 `ctx->disp_fps`：实时速度；
- `ctx->results->size()`：当前模型结果数量；
- `ctx->frame->cols/rows`：logic 实际取得的图像大小。

所有指针都先检查再使用。模型暂时没有结果时应显示 `result count: 0`，不能崩溃。

#### 本节产出

- [ ] 主项目画面能持续显示上述系统数据；
- [ ] 一张推理开启时的截图；
- [ ] 一张推理关闭时的截图，能看到 logic 仍在运行；
- [ ] 一张“系统数据读取表”，写清本课每个值从哪个 `ctx` 字段取得。

#### 通过标准

代码中没有把通道号、FPS、当前时间或结果数量重新声明成自定义参数；空帧和空结果均能安全处理。

### L3 · 自定义业务参数，并让 Web 自动显示控件

#### 本节目标

为人员停留规则增加可配置值，并从 Web 修改这些值。

#### 学习与操作

在主项目 `logic.json` 中增加：

| 参数 | 类型 | Web 中的含义 | 保存新值时怎样处理已有状态 |
|---|---|---|---|
| `roi_name` | `string` | 要关注的区域名称 | 清空旧计时 |
| `dwell_sec` | `number` | 连续停留多少秒后触发 | 清空旧计时 |
| `cooldown_sec` | `number` | 两次触发之间至少间隔多久 | 清空旧计时 |
| `show_overlay` | `boolean` | 是否显示业务状态 | 保留当前计时 |
| `alarm_message` | `string` | 事件中显示的业务说明 | 保留当前计时 |

每个参数都要有默认值、简单易懂的中文名称、合理范围，并说明保存新值后是否清空当前计时。例如：

```json
"dwell_sec": {
  "type": "number",
  "title": "停留触发时间",
  "description": "目标在指定区域连续出现多少秒后生成事件。",
  "minimum": 0.5,
  "maximum": 300,
  "default": 5,
  "x-step": 0.5,
  "x-unit": "秒",
  "x-hot-reload": "reset_state"
}
```

C++ 中使用与类型对应的方法：

```cpp
const std::string roi_name = ctx->param_string("roi_name");
const float dwell_sec = ctx->param_float("dwell_sec");
const float cooldown_sec = ctx->param_float("cooldown_sec");
const bool show_overlay = ctx->param_bool("show_overlay");
const std::string alarm_message = ctx->param_string("alarm_message");
```

本课不把目标类别和 YOLO 置信度重复声明为 logic 参数。课程统一在 Web 模型节点中设置 `detect_classes=["person"]` 和 `obj_thresh`，logic 在下一课直接读取 `result.label` 与 `result.score`。

三种参数更新方式用简单语言理解：

- `preserve_state`：新值立即使用，当前计时继续；
- `reset_state`：新值立即使用，但当前业务计时从头开始；
- `restart_required`：运行中不采用新值，重启程序后再使用。本课程主项目通常不需要它。

#### 本节产出

- [ ] 主项目 `logic.json` 中包含上表五个业务参数；
- [ ] `logic.cpp` 使用正确的 `param_*()` 方法读取五个业务参数；
- [ ] Web 自动显示文字框、数字框和开关，不修改前端代码；
- [ ] Web 保存 `show_overlay` 后画面立即变化；
- [ ] 一次输入越界值后被拦截或拒绝的记录。

#### 通过标准

参数默认值、Web 默认值和 C++ 默认行为都来自当前模块的 `logic.json`；没有手改生成后的 `logics.json`。

### L4 · 处理模型结果和命名 ROI

#### 本节目标

读取模型已经筛选好的结果，再找出位于指定区域内的目标。

#### 学习与操作

认识 `AlgoResult` 中最常用的内容：

- `label`：YOLO 输出的类别名称；
- `score`：YOLO 输出的置信度；
- `box`：目标框；
- `track_id`：跟踪编号。

业务步骤：

1. 在 Web 模型节点中把 `detect_classes` 配置为 `person`，并设置合适的 `obj_thresh`；
2. 遍历 `*ctx->results`；
3. 直接读取每个结果的 `result.label`、`result.score`、`result.box` 和 `result.track_id`；
4. 用 `roi_find(ctx, roi_name.c_str())` 找到 Web 中画出的区域；
5. 用 `roi_contains(ctx, result.box, roi_index)` 判断目标框中心是否在区域内；
6. 从区域内的结果中选择置信度最高的一个；
7. 用红框突出目标，在画面显示模型实际输出的类别、分数、区域名和跟踪编号。

`detect_classes` 中的类别名称必须与当前模型的 `labels.txt` 完全一致。低于 `obj_thresh` 的结果在进入 logic 前已经被模型过滤。没有 ROI、没有目标或找不到区域时，都要显示清楚的等待状态。

#### 本节产出

- [ ] Web 中创建一个有名称的 ROI；
- [ ] Web 模型节点配置了 `detect_classes` 和 `obj_thresh`；
- [ ] 主项目直接显示 `result.label` 和 `result.score`，没有复制成同义 logic 参数；
- [ ] 主项目能从模型结果中筛选出位于 ROI 内的目标；
- [ ] 目标在区域外时不进入业务判断；
- [ ] 区域内有多个目标时，只突出当前选中的目标；
- [ ] “没有结果、找不到 ROI、目标不在区域”三种状态的截图。

#### 通过标准

修改模型节点的 `detect_classes` 或 `obj_thresh` 后，logic 收到的结果随之变化；模块没有重复定义默认的目标类别和置信度阈值。筛选逻辑面对空结果和错误 ROI 名称不会崩溃，检测框与 ROI 可以直接比较。

### L5 · 保存每个通道自己的计时和触发状态

#### 本节目标

把“当前帧发现目标”扩展成“目标连续停留 N 秒后只触发一次”。

#### 学习与操作

在主项目中定义简单状态：

```cpp
struct PersonDwellState
{
    int active_track_id = -1;
    uint64_t first_seen_ms = 0;
    uint64_t cooldown_until_ms = 0;
    bool triggered = false;
};
```

第一次运行时把它放进 `ctx->state`。之后每一帧都从同一位置取回。状态至少覆盖：

1. 等待目标；
2. 正在计时；
3. 已经触发；
4. 冷却中；
5. 目标离开后复位。

课程主项目一次跟踪一个选中的目标。选中的 `track_id` 变化时，应结束旧目标的计时，再为新目标重新计时，不能把两个人的停留时间加在一起。如果当前模型没有可靠的跟踪编号，应把规则明确改成“区域内持续有人”，不要假装它是在跟踪同一个人。

计时间隔使用 `ctx->timestamp_ms`。不要使用函数内的可变 `static` 保存状态，因为那会让多个通道共用同一份计时。

本课先用画面文字和日志表示“应当触发”，还不真正上报。

#### 本节产出

- [ ] 一个由 `ctx->state` 保存的 `PersonDwellState`；
- [ ] 画面显示“等待、计时、已触发、冷却”四类状态；
- [ ] 画面显示当前已停留秒数和目标跟踪编号；
- [ ] 连续停留达到阈值时只出现一次触发日志；
- [ ] 目标离开、重新进入和冷却结束后的操作记录。

#### 通过标准

同一个目标持续出现不会逐帧触发；目标离开后可以按规则重新开始；代码中没有用全局变量或可变 `static` 保存每通道业务状态。

### L8 · 绘制告警内容并创建本地事件

#### 本节目标

把 L5 的“应当触发”变成真正的业务事件，并让事件带上正确图片和字段。

#### 学习与操作

本课先使用教师准备好的一条图片接口契约和连接 Profile，或临时在 Web 中连接对应上报节点。
这里只验证“logic 能创建本地事件和图片”；接口契约编写与远端联调放到 L9 再讲。

先在画面上绘制，再调用上报：

```cpp
if (!hit)
    return;

draw_rect(ctx, hit->box, cv::Scalar(0, 0, 255), 3,
          1.0, DrawCommand::MEDIA);
draw_text(ctx, "人员停留告警", cv::Point(20, 60),
```

## 六、新手开发时最常见的错误

| 现象 | 常见原因 | 应怎样修改 |
|---|---|---|
| Web 找不到新 logic | 只改了源码，没有重新打包/安装；或源 `logic.json` 缺失 | 核对 `REGISTER_LOGIC()` 的函数名、清单检查结果和已安装 `logics.json`，再重新构建 |
| Web 没出现新参数 | 参数没有写在模块 `logic.json.parameters`，或 Web 仍读取旧安装包 | 检查模块中的 `logic.json`，并更新应用包 |
| C++ 读取参数失败 | `logic.json` 类型与 `param_*()` 不匹配，或参数名拼错 | 按类型表修改，并运行清单检查 |
| 多个通道计时串在一起 | 用了可变 `static` 或全局变量 | 改用每通道的 `ctx->state` |
| 每帧都产生一条事件 | 没有“已触发”标记、冷却或目标去重 | 在 state 中增加已触发标记和冷却时间 |
| 找不到目标 | 模型节点的 `detect_classes` 与 `labels.txt` 不一致，或 `obj_thresh` 过高 | 先核对 Web 模型节点，不要在 logic 中重复增加同义参数 |
| ROI 判断不对 | ROI 名称错误，或重复换算坐标 | 使用 `roi_find()` 和 `roi_contains()` |
| 告警图片没有业务标注 | 在 `report_event()` 之后才调用 `draw_*()` | 调整为先绘制、后上报 |
| `report_event()` 未接受 | 根据 `status/detail` 区分策略关闭、无投递、无效请求、worker 或存储失败 | 先读结构化结果，再检查对应配置或系统资源 |
| `accepted()` 为真但远端没收到 | 事件只完成了本地创建，远端投递失败或仍在处理 | 查看该事件每条投递的状态和错误信息 |
| 换服务器还要改 C++ | 把 URL、密钥或 HTTP 写进了 logic | 移到 Web/上传 Profile 配置 |
| 推理关闭后 logic 崩溃 | 默认认为 `results` 一定有内容 | 对空结果做正常处理；传统 CV 使用 `frame` |

| ROI 进入与简单上报 | [ROI 告警代码模式](skills/rk3588-channel-logic/references/examples/roi-alarm-pattern.md) | 这是代码模式而非内置模块；真实业务要补停留、冷却和复位规则 |
| Web 按钮触发多种上报 | `logic_upload_teach` | “上报配置”节点决定图片、视频和投递目标，logic 不直接处理上传 |
| SOP 专用流程 | `logic_path_sop` | 它有专用 Web 画布，完整流程保存在 `logic_parameters.flow`，不是普通模块模板 |

## 八、选修内容

以下内容属于完成普通上层 logic 之后的扩展，不放进必修主线：

- pose/seg：使用关键点或分割结果完成姿态、穿戴或覆盖率规则；
- 多 ROI：入口区、工作区、危险区之间的组合判断；
- 跨通道规则：一个通道读取其他通道的安全快照；
- SOP：步骤、分支、循环、停留和专用 Web 画布；
- 更复杂的传统 CV：颜色、轮廓、帧差、背景建模；
- 自定义 Web 控件：通用参数表单无法满足时再修改前端；
- 新上报协议：现有服务器/Dify 组合不能满足时再扩展服务层；
- 底层性能与部署：解码、RGA、NPU、编码、线程和 systemd。
