## 改了哪里

此前模型完成 NPU 运算后，CPU 读取输出、扫描类别、生成检测框或分割掩码时，仍占着核心锁。
其他模型即使准备好了输入，也要等这段 CPU 工作结束。

现在每个模型保留自己的输出缓冲区。可以使用原生输出时，由 NPU 直接写入该缓冲区，
同步推理完成就交还核心；CPU 随后在锁外重排数据、转换数值并做后处理。
INT8 输出的重排使用 ARM NEON，保持每个量化值不变。
同一模型对象仍由实例锁保护，保证下一帧不会覆盖正在读取的数据。

同核调度仍然串行保护 SDK；不同核心并行。释放核心时只通知能取得核心的等待线程，
停止和驱动故障时唤醒全部等待线程。同核提交保护通过了并发回归检查。

普通输入和 DMA 输入共用这套输出管理。CPU 回退直接写入已经绑定的输入缓冲区，
避免 `rknn_inputs_set` 替换 DMA 绑定后继续读取旧帧的问题。
YOLO26 Depth 的原生 FP16 方案未通过深度结果逐字节对照，已经撤回；它保留原来的浮点读回。

## 如何读测试结果

- **推理 FPS**：每秒成功处理的帧数。多模型组合按一帧全部模型完成计算，另统计模型调用次数。
- **发布 FPS**：每秒真正写入结果槽、供后续业务使用的结果数。旧帧被丢弃时可能低于推理 FPS。
- **NPU 占用**：逐秒读取驱动的三个核心负载，再分别取平均。
- **CPU 占用**：100% 表示占用一个 CPU 核心，300% 约为三个核心。
- **queue+worker**：入队到推理处理完成的时间，包含排队；不等于网络端播放延迟。
- 日志里的 **rknn** 耗时包含等待核心锁，不能直接当成模型的纯 NPU 耗时。

`max_fps=25` 会限制应用提供的工作量。比如 3 路轻量模型已经各自处理约 25 帧/秒，
NPU 还有空闲属于正常情况；增加到 15 路后才能检验是否有足够工作把三核压满。
达到视频帧率后，应以业务帧率和处理延迟判断性能。

## 自己复测

先正常停止当前推理程序，确保测试进程可以独占 NPU 和 8554 端口，然后在仓库根目录运行：

```bash
python3 engine/tests/inference/run_live_capacity.py \
  --binary build/engine/vision_analysis \
  --app /opt/ai_apps/test_obb \
  --config /opt/ai_apps/test_obb/assets/depth_multi_model.json \
  --output build/performance-live-new \
  --warmup 15 --seconds 60
```

`--binary` 是要测的应用程序；`--app` 提供运行目录、assets 和 libs；`--config` 是完整业务配置。
`--output` 必须使用一个尚不存在的目录。脚本复制配置，启动实际应用和 RTSP 客户端，
预热后统计每路成功推理、发布、耗时和三核负载，最后正常停止应用。
`result.json` 的 `valid` 只有在各路正常出结果、RTSP 持续传输、程序正常退出时才为真。

本次完整模型清单位于 `build/performance-15ch/models.json`。矩阵测试使用 `run_live_matrix.py`，清单包含 `name/model_type/model_path/label_path`，
按 3/15 路遍历全部模型，并覆盖 1/6 路、混合视频通道和同帧多模型组合。
同一场景的两份程序使用相同配置，逐路核对发布帧率和处理耗时。
