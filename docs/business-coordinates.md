# 固定业务坐标与模型输入尺寸

框架把业务坐标固定为完整画面的 **640×640**，定义位于
`engine/src/common/business_coordinates.h`。该坐标与视频原图、NPU 输入独立，
不由首个模型、通道顺序、模型热切换或重启决定。

| 数据 | 坐标 / 尺寸 |
| --- | --- |
| `.rknn` 实际输入、模型内部解码结果 | 由模型张量属性决定 |
| 业务可见检测框、关键点、分割掩码、跟踪结果 | 完整画面的 640×640 |
| 业务 ROI、自定义 `draw_*` 指令、像素距离 / 面积阈值 | 640×640 业务单位 |
| `ctx->business_frame()` / `ctx->model_frame()` | 同一份惰性 640×640 BGR 缓存 |
| `ctx->source_frame()` | 视频原图真实宽高 |
| 实时显示、带叠加的上报图片和录像 | 输出可以不同尺寸，叠加统一从业务坐标缩放 |

## 推理路径

原始 DMA-BUF 经 RGA 按实际模型尺寸直接写入 RKNN 输入内存。固定业务画布不会
在这条零拷贝路径中提前生成 BGR，也不会将 640 图像再放大作为 960 输入。
CPU 回退在模型输入为 640 时复用业务缓存；其他输入尺寸从原始缓冲直接生成，
由各模型 worker 独立复用输出内存，不先生成完整原图 BGR 再缩放。

框架在 tracker / logic 之前统一转换结果。整帧直接拉伸的 960×960 输入中，
`(480,480)` 映射为业务中心 `(320,320)`。ROI 推理还需要先去除模型补边、还原
原图取景位置，再映射到完整业务画布；不能单纯对所有 ROI 结果乘 `640/960`。
包围框边缘使用 floor / ceil 保留覆盖范围，缩放取整可能产生一个业务像素的差异。

常用 640 整帧结果采用身份变换快速路径，保持原检测框并裁剪画面边界，
不分配或复制分割掩码。需要缩放的整帧掩码直接生成目标尺寸；局部掩码直接写入
业务画布对应区域，避免中间缩放图的再次复制。整帧 / ROI 双批次需要合并掩码时，
才创建可写副本。

## 业务代码与兼容接口

已有 `(320,320)`、以 640 画布定义的 ROI 和像素阈值可以继续使用。新代码推荐：

```cpp
const cv::Point center = ctx->business_center();
const cv::Size size = ctx->business_size();
draw_circle(ctx, center, 100, cv::Scalar(255, 0, 0));

// 只需要检测结果或绘图时，无需取图。
// 首次调用才生成业务图；后续调用复用缓存。
const cv::Mat *frame = ctx->business_frame();
```

通道和全局上下文均提供 `business_width()`、`business_height()`、`business_size()`、
`business_center()`。历史 `model_frame()`、`inference_get_input_w/h()`、全局上下文
`model_width/model_height` 保留，但表示业务画布，不表示实际 NPU 输入。

直接处理原图的业务仍须使用原图坐标。完整画面的业务点 `(x,y)` 对应原图中的
`(x*src_width/640, y*src_height/640)`。更改摄像头取景、镜头或业务裁剪后，物理测量
标定仍需检查。以非 640 画布生成的历史标定数据也需重新换算或采样。

该机制与模型解码器的兼容性是两件事：`yolov5_seg` 的固定原型尺寸和同通道多模型
必须同输入尺寸的限制仍需后续单独改进。

## 控制台模型检查与生效状态

选择模型节点后，侧栏分别显示：

- **业务坐标**：固定 640×640，中心 (320,320)。
- **所选模型输入**：从真实 RKNN 输入张量读取宽、高和 NHWC/NCHW 布局，文件名不能决定输入尺寸。
- **实际运行**：从运行中引擎的模型实例读取尺寸和路径，并标明正在运行的配置文件。

修改选择或保存另一份配置并不代表模型已经生效。
同名覆盖模型文件不会改变配置中的路径，现有配置监控不会因此自动重载模型；
控制台会对比所选文件与已加载实例的文件版本并提示重启程序。

热切换期间状态为 `loading`；成功后才更新实际模型。加载失败时报告错误并保留已恢复的
原模型信息。如果原推理线程也无法恢复，则清空已确认运行模型，不显示成功。
初次模型加载失败和需要重启才能变更线程数量的情况也会返回错误状态。

保存配置和另存为均在写文件前校验启用通道中的启用模型，包括模型可读性、单输入、
batch=1、三通道、四维 NHWC/NCHW 输入，以及现有解码器的基本输出张量约定。
同一通道的多个模型必须使用相同输入宽高；不同通道允许使用不同尺寸。
`yolov5` / `yolov5_seg` 当前要求 NHWC 输入，分割模型还要求固定的 32×160×160 proto。
校验失败返回具体通道、模型与原因，原配置文件保持不变。空白草稿和关闭推理的通道可正常保存。
这些结构检查不能代替真实权重的精度、数值正确性和吞吐验证。

控制台模型路径限定在本程序 `assets/` 内，使用 `assets/name.rknn` 相对路径。
原先手写的外部绝对路径需在控制台编辑前将模型导入程序的 `assets/`。
离线检查命令为：

```bash
./vision_analysis --inspect-model assets/yolov8n.rknn
```

命令只加载 RKNN 并查询属性，不启动采集、显示或运行推理；以 `MODEL_INFO_JSON=` 开头
的一行是 JSON 结果，退出码 0 表示基础输入检查成功，非 0 表示失败。
模型类型对应的输出兼容性由后端在所选类型确定后检查。
控制台新接口为 `GET /api/apps/{name}/models/info?path=assets/name.rknn&model_type=yolov8_det`
和 `GET /api/apps/{name}/models/runtime`。

未运行模型由独立检查进程读取，按模型和引擎文件的 inode、大小、修改时间、状态变化时间缓存，
覆盖上传或更新引擎会失效；失败缓存 30 秒后允许重试。并发请求合并，每个后端进程最多同时运行一个检查进程，
缓存最多 128 个条目。模型节点侧栏打开时，每两秒查询一次已保存的运行状态；页面隐藏时停止查询。
运行状态使用独立互斥锁，只在加载、重载、停机时写入，不参与逐帧推理、结果映射或显示。
首次未缓存检查会短暂加载额外 RKNN 上下文，因此仍有一次性的加载和内存成本。

使用该功能需要一起更新引擎程序包、控制台后端和前端。旧引擎缺少检查命令或运行状态协议时，
控制台明确提示更新；不会把配置里的尺寸当成已经生效的模型尺寸。

## 回归验证

```bash
cmake -S engine -B build/engine \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_INFERENCE_ROI_TESTS=ON \
  -DBUILD_FRAME_SNAPSHOT_TESTS=ON \
  -DBUILD_PERFORMANCE_TESTS=ON
cmake --build build/engine -j4
cd build/engine
ctest --output-on-failure
```

`business_coordinates_regression` 覆盖 640 / 960 / 非正方形输入、固定中心、
ROI stretch / letterbox / expand、补边结果过滤、关键点、掩码尺寸与像素对齐、
惰性业务图兼容接口、实际模型尺寸输出内存复用、原图单像素细节保留，以及显示 / 图片 /
录像三种出口的叠加坐标。软件 BGR / RGB 同时验证当前 RGA 枚举和旧软件帧编码。

首批板端验证中，主程序及 12 项 CTest 回归全部通过；另用合成模型替换工厂，实际执行
生产推理 worker 的 640→960→640→960 热重载以及以 960 首次启动，验证业务坐标、
业务图和掩码均保持 640。合成模型验证不代表真实 960 RKNN 权重的精度或吞吐测试。
仓库当前六个 RKNN 模型的实际输入均为 640×640。

第二批验证中，主程序、前端生产构建、13 项 CTest 均通过；新增后端回归覆盖并发请求
合并、缓存失效、布局兼容性、无效路径、保存前校验和实际运行状态读取。
另启动真实 RKNN 引擎验证 107→106 成功切换、无效 RKNN 被保存前拦截、绕过控制台
手写无效配置后恢复 106，以及修正配置后重新加载 107；实际状态均与生效实例一致。
连续 30 次选择 / 保存检查没有再次执行 RKNN 检查进程。合成 640/960 模型通过生产
worker 验证失败后继续产出业务结果、线程数量变更拒绝、禁用 / 重新启用和反初始化后启动。
全量后端测试中原有存储清理测试仍失败：测试将待发送事件设为可删除，而清理实现保护待发送事件；
该测试单独运行也失败，与模型改动无关，未在本批修改存储清理行为。

## 板端性能对比（2026-10-08）

使用改动前保存的显示微基准与当前版本，固定测试进程在 CPU 4，OpenCV 使用一个线程。
每个版本交替测量三次，每次每种性能显示状态提交 480 个通道帧；下表为各次平均耗时的中位数。
视频源为 1280×720，四通道窗口各为 960×640，使用真实 RGA 和绘图函数。

| 显示场景 | 改动前（微秒/通道帧） | 改动后（微秒/通道帧） |
| --- | ---: | ---: |
| 性能文字关闭 | 4270.77 | 4255.80 |
| 性能文字开启 | 4523.54 | 4512.97 |

两种场景差异均小于 0.4%，未见明显显示性能回退。未固定 CPU 核时，两个版本均出现约
4～7 毫秒的调度波动，因此不使用那组结果判定改动开销。CPU 频率仍未锁定，这些微小差异
不作为稳定的提速承诺。复现当前显示测试需启用 `BUILD_PERFORMANCE_BENCHMARKS=ON`，执行
`taskset -c 4 build/engine/display_performance_benchmark 120`。

坐标映射使用改动前的生产函数与当前函数单独比较，目标画布均固定为 640；每帧包含
20 个结果，检测/姿态各测量 20000 帧，单张分割掩码测量 200 帧，各交替三次。
该测试未固定 CPU 核，以下仅说明操作量级，不代表完整 NPU 推理耗时：

| 输入 / 结果类型 | 改动前（微秒/帧） | 改动后（微秒/帧） |
| --- | ---: | ---: |
| 640 / 检测 | 2.570 | 2.252 |
| 640 / 每个结果含 17 个关键点 | 3.113 | 2.738 |
| 640 / 单张整帧掩码 | 240.587 | 1.234 |
| 960 / 检测 | 1.243 | 1.319 |
| 960 / 每个结果含 17 个关键点 | 3.132 | 3.168 |
| 960 / 单张整帧掩码 | 641.364 | 416.418 |

640 掩码的改善来自跳过身份变换的图像复制；960 掩码仍需实际缩放，但减少了中间画布复制。
原始日志位于本次本地验证目录 `/tmp`，不作为仓库资产提交。上述测试不包含采集、RTSP 编码
或实际 960 RKNN 权重推理，较大模型本身的 NPU 成本需另测。
