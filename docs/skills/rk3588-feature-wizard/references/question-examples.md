# 精简需求访谈与参考写法

本页限制向导的提问数量。框架字段仍要完整，但优先由源码、现有清单和有依据的推荐填充，不得把内部
需求合同逐项改写成用户问卷。

## 数量上限

- 环境确认通常 1 轮，只接受“是”或“否 + 简短纠正”；检测错误且用户只答“否”时，最多追加 1 个
  环境选项题；
- 业务访谈通常 2–3 轮，硬上限 4 轮；初始描述已经明确的内容直接跳过；
- 达到上限仍有阻塞性歧义时，列出未决项并停止，不继续追加问卷，也不擅自编码；
- 用户回答“不知道”时，先查源码，再提出一个具体推荐让用户回答“是/否”。
- 推荐必须能完全落在 Logic 写入白名单内；需要修改公共框架、Web 或服务的需求直接说明本向导不实施，
  不追加“是否允许扩大权限”的问题。

## 环境确认

展示自动检测结果，并把本仓库的默认部署目标作为建议而非事实：

```text
检测到当前开发环境为 Linux RK3588；默认按 RK3588 Linux 部署。是否正确？
回复“是”即可；不正确可简短回复，例如：“否，当前是 WSL2，最终仍部署 RK3588。”
```

不要要求用户填写 Python、工具、摄像头、NPU、GPIO 和远端服务清单。命令与设备能否访问由代理按需求
只读检查；无法验证的硬件直接记为“待实机验证”。只有某项硬件会改变功能设计时，才追加一个简短确认，
例如：“这个功能需要 GPIO，目前能连接 GPIO 实机验证吗？回复是或否。”

## 三个业务主问题

### 1. 业务目标

仅当初始描述不足以确定结果时询问。不要只让用户说一个功能名，要用一个自然语言场景同时取得“现场、
关注对象、业务事件、系统结果、结果使用者和有效标准”；2–4 句话即可，不要求技术术语：

```text
请描述一个具体业务场景：在什么现场，谁需要关注什么对象；发生什么情况时，系统应自动做什么；结果由
谁在哪里使用，怎样算真正解决了问题。2–4 句话即可，不需要说明模型、代码或接口。

例如：“仓库夜间无人值守，值班人员需要及时发现进入危险装卸区的人。有人进入并持续停留时，系统应
立即提醒值班人员并留下能看清现场的记录；值班人员能据此确认和处置，且人员短暂路过不频繁误报。”
```

示例只展示回答粒度，不默认用户一定要做人员 ROI 报警。不得在问题末尾罗列“还支持 GPIO、跨通道、
周期上报”等能力菜单；用户确实没有方向时，才根据其行业或现场给最多 3 个业务场景供选择。

不要同时要求用户解释通道、模型、ROI、具体阈值、上报协议和测试命令；这些由后两问基于源码给出推荐。
如果用户仍只回答“做一个报警/统计功能”，先把其回答扩写成一个明确的推荐场景让用户确认，不要直接把
空泛目标带入实现。

### 2. 行为方案

先查源码，再把通道范围、识别输入、触发、复位、重复、断流等合成一个具体推荐：

```text
建议按单通道 person + Web ROI 判断：人员连续进入 3 秒报警，离开 2 秒复位，同一人员复位前不重复，
断流时清除计时。是否按这个方案实现？回复“是”；如需调整，只写不同之处。
```

推荐中的数字只能标为建议，用户确认后才能成为需求。能从源码确定的标签、字段或扩展点不要询问。

### 3. 交付方案

把参数、绘制、事件媒体、现有 Adapter 上报、metadata 驱动 Web 和验收合成一个具体推荐，只保留与
需求相关且能在模块目录内表达的项目：

```text
建议在 Web 配置持续时间，画面显示 ROI 和计时；报警保存带标注图片并进入待上报记录，不接远端接口；
用进入、短暂停留、离开、再次进入四种录像场景验收。是否按这个方案实现？回复“是”；如需调整，
只写不同之处。
```

不需要上报、Web、按钮或 GPIO 时直接写入推荐为“不需要”，不再分别追问。任何公共引擎、Web 源码或
服务改动都超出本向导写入边界，不能作为可选推荐。

## 允许的第 4 个业务问题

只在以下情况使用，并提供 2–4 个短选项或一个推荐方案：

- 用户否定方案但没有说明哪里不同；
- 两种实现会产生明显不同的业务结果；
- 缺少无法从仓库取得的远端协议、硬件电平或外部契约。

示例：“报警需要哪种媒体？1. 带标注图片（推荐） 2. 原图 3. 视频 4. 纯数据。回复数字即可。”

## 内部合同不是问题清单

代理仍需在内部补全环境、运行层、输入、触发、状态、输出、事件、远端、Web 和验收字段。来源依次是：
用户原始描述、当前源码与清单、用户确认的推荐、明确标注的安全假设。只有会改变业务结果且无法推荐的
最后一个差异才允许提问。
