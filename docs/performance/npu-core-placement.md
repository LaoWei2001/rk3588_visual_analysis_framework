# 自动核心分配：RTSP / USB 实机对照

历史实测：2026-10-26。“旧版/新版”均指当时记录的版本，不代表当前构建；当前调度规则以链接中的实现说明和源码为准。

[首页](../../README.md#性能与验证) · [Benchmark](benchmark.md) · [调度规则](../../engine/src/vision/inference/NPU_SCHEDULING.md)

## 问题与修正

旧版每个自动模型独立使用 `(channel + worker + model_index) % 3` 分配核心。
ZipDepth 的三个 worker 因而会使用核心 0/1/2，即便其他两路已经显式指定核心 1/2。
进程级核心互斥能防止不安全的同核 SDK 并发，但按请求公平不等于按耗时分配预算：
一次较慢的深度任务会延长后面的检测任务等待。

修正后的规划读取完整配置，自动模型先避开显式核心；自动通道数等于剩余核心数时，
按通道 ID 各分一个核心。“自动 / 固定 1 / 固定 2”与三路全自动在该三路配置下都分成 0/1/2。
单路、两路全自动以及四路以上仍保留原来的均衡共享，避免引入不等长核心队列。
核心规划依据配置中的通道与模型条目，不按 ZipDepth 文件名或模型类型特判。

分配只在初始化和热更新时计算，不增加逐帧选核成本，没有放宽 `npu_execution.h` 的保护，
也没有改变模型、输入尺寸、精度、跟踪、限帧或系统频率。改变其他通道的显式核心也会
触发自动通道重分配；模型加载失败后按回退的实际配置重新协调。

资源隔离会改变各路的预算。ZipDepth 从三核退回一个核心时，自身吞吐会降低，
其他两路恢复独立核心的速度；**不能把这一结果表述成所有模型 FPS 同时上涨**。
两路全自动仍会互相竞争；需要明确隔离时可手动指定核心。三个核心都已指定或通道数
超过可用核心数时继续安全共享，无法承诺任意组合零等待或每路都保持三核吞吐。

## 实测条件

| 项目 | 条件 |
| --- | --- |
| 平台 | 本机 RK3588 EVB7 LP4 V10，约 8 GB RAM，Debian 11，内核 `5.10.160` |
| NPU | RKNN Runtime `2.4.2a2`，driver `0.9.0`；未调整频率/governor |
| 输入 | 用户提供的同一个局域网 RTSP 摄像头与 USB `/dev/video81`；具体 URL/账号未公开 |
| 解码复用 | 两个相同 RTSP 配置共享 `DecChannel`；扩展矩阵是逻辑分析通道数，**不是六台独立摄像头解码压力** |
| 基础三路 | RTSP → ZipDepth 768×768 FP16；USB → YOLOv5n 640×640；RTSP → YOLOv8 Pose 640×640 |
| 扩展六模型 | 基础三模型 + YOLOv5 Seg、YOLOv8 Det、YOLO26 Depth，新增模型均为 640×640 |
| 分析与输出 | 每通道 3 worker，queue=1，max_fps=25，SORT 开启；HDMI 开启，1280×720；H.264 RTSP 输出由 TCP FFmpeg 客户端持续解码 |
| 网格 | 基础三路 2×2；扩展一路/两路/四路/六路/同帧组合为 1×1 / 1×2 / 2×2 / 2×3 / 1×1 |
| 时间 | 基础对照预热 15 秒、采集 60 秒，每版本一次；扩展每次预热 15 秒、采集 30 秒，2/4/6 路每版本两次并反转顺序，单路/同帧组合各一次 |
| 统计 | 排除跨预热边界窗口，以窗口实际秒数计算 FPS；queue+worker 按成功任务数加权 |

CPU 100% 为引擎占用一个逻辑 CPU 核心，不包含 FFmpeg/Web 服务。RTSP 解码帧计数
包含预热及连接阶段，不能据此推算测量窗口内的视频 FPS。输入为实时画面，两版本并非
逐帧相同内容；短窗口波动不能被当成精确的不降证明。风扇、室温、独立摄像头长时负载
未完整记录，端到端 P50/P95、完整 RSS/PSS/CMA 曲线和统一丢帧率未测量。

基础三路的 `[Feed][ch01]` 实际 USB 收帧约 17.2 FPS，新版该路没有 pending 淘汰；
约 17 FPS 是此次视频源条件下的整管线成绩，不能作为 YOLOv5n 的裸模型吞吐上限。

`yolov5n.rknn` 和 `yolov5_seg.rknn` 的检测头为 80 类，而用户配置的标签文件各只有三行。
本轮保留标签以保证 A/B 条件一致；这些成绩只说明推理/发布和调度，**不证明类别语义正确**。
实际业务应另配与权重一致的标签和后处理契约；本次不改写用户配置。

## 基础三路对照

单元格为 **成功推理 FPS / 结果槽发布 FPS**，不是 RTSP 播放帧率。

| 版本 / 核心配置 | ZipDepth | YOLOv5n USB | YOLOv8 Pose |
| --- | ---: | ---: | ---: |
| 旧版固定 0/1/2 | 3.99 / 3.99 | 17.19 / 17.19 | 24.80 / 24.80 |
| 新版固定 0/1/2 | 4.04 / 4.04 | 17.19 / 17.19 | 24.77 / 24.77 |
| 旧版自动 / 1 / 2 | 10.28 / 8.34 | 10.47 / 10.47 | 9.03 / 9.03 |
| 新版自动 / 1 / 2 | 4.00 / 4.00 | 17.17 / 17.17 | 24.92 / 24.92 |
| 旧版三路全自动 | 10.25 / 9.55 | 10.44 / 9.45 | 10.30 / 9.53 |
| 新版三路全自动 | 4.03 / 4.03 | 17.21 / 17.21 | 24.99 / 24.99 |

只将 ZipDepth 设为自动时，检测/姿态恢复到手动分核水平；对应的 queue+worker 均值
由 **271.80 / 337.34 ms** 降到 **17.91 / 27.46 ms**。这不是摄像头到浏览器的端到端延迟。
三路成功推理吞吐合计从约 29.78 到 46.09 帧/s，但 ZipDepth 核心预算由三核变成一核，
它的自身吞吐下降，不能省略此条件。此场景引擎 CPU 约 219.50% → 173.71%，同样受预算变化影响。

固定配置的核心映射和逐帧执行没有变化；两次短测存在约百分之一量级波动，
不宣称所有指标严格零回退，也不声称完成长期稳定性验收。

## 不同路数与模型组合

顺序为 ZipDepth / YOLOv5n USB / YOLOv8 Pose / YOLOv5 Seg / YOLOv8 Det / YOLO26 Depth；
前 N 路取前 N 个模型。2/4/6 路合并两轮反向顺序的实际窗口计数；单路与同帧各一轮。

| 场景 | 旧版成功吞吐合计 | 新版成功吞吐合计 | 新版每路发布 FPS |
| --- | ---: | ---: | --- |
| 单路 ZipDepth | 11.53 帧/s | 11.82 帧/s | 10.72 |
| 两路自动 | 23.19 帧/s | 22.95 帧/s | 10.59 / 10.31 |
| 四路自动 | 34.62 帧/s | 34.53 帧/s | 8.03 / 7.84 / 8.14 / 7.92 |
| 六路自动 | 33.87 帧/s | 34.01 帧/s | 5.44 / 5.38 / 5.29 / 5.39 / 5.28 / 5.35 |
| 同帧六模型 | 5.50 批/s | 5.52 批/s | 5.52 批/s |

这些场景保持原版核心映射，没有增加逐帧调度操作。短测仍有升降：两路 USB 推理
11.94 → 11.65 FPS，四路 USB 发布 8.17 → 7.84 FPS，六路最后一路发布 5.43 → 5.35 FPS。
**不能据此宣布严格“任何组合、任何指标零回退”**；完整逐路对照保留在 JSON，
没有只选择上升项。固定场景与用户问题的主要改善应和这些共享负载分别判断。

22 次完整管线运行均无记录到的 RKNN/推理异常，各路持续发布、RTSP 持续解码并正常停止；
另有七步热更新/失败回退检查。六类权重各通过三个同核实例的普通输入及 DMA 入口验证。
YOLO26 Pose 缺少权重，只有编译/公共调度测试证据；未穷举任意网络与任意组合。

NPU 利用率为采样快照。核心等待、输入供帧、CPU 后处理、内存处理和输出发布都会影响
整管线吞吐；日志 `rknn` 还包括核心等待，不能直接视为裸 NPU 执行时间。
本次保留 SDK 输入至输出释放的完整互斥周期，部分后处理仍在此周期内，
未用提前解锁换取占用率。详细均值与边界见 [Benchmark 指标口径](benchmark.md#指标口径)。

## 复现

在空闲 RK3588 上准备含 `libs/assets` 的隔离应用、三个启用且各含一个模型的基础配置，
以及六个模型配置节点组成的 JSON 数组 manifest。基础配置前两路分别为可用 RTSP 和 USB，
manifest 顺序为 ZipDepth / YOLOv5 / YOLOv8 Pose / YOLOv5 Seg / YOLOv8 Det / YOLO26 Depth。
权重不会随报告自动提供；所有路径均需替换为本机实际资源。

```bash
python3 engine/tests/inference/run_core_placement_matrix.py \
  --baseline /path/to/old-engine --candidate /path/to/new-engine \
  --app /path/to/isolated-app --config /path/to/three-channels.json \
  --manifest /path/to/six-models.json --output /path/to/new-private-report \
  --cases fixed first_auto all_auto one two four six composite \
  --warmup 15 --seconds 60 --repeats 2
```

脚本交替运行版本，检查每路持续完成/发布、零推理失败、RTSP 继续解码及正常停止；
`summary.json` 列出各路推理/发布/均值变化，**脚本结束不代表每个性能指标都提高**。
输出目录为私有权限，但日志/配置可能包含摄像头账号，发布前仍须脱敏。
本页扩展首轮使用 `--seconds 30 --repeats 1`，2/4/6 路另补一次反向顺序；
没有冒称已经执行上述更长的 60 秒全矩阵。

热更新与加载失败回退可以单独验证，脚本只更改新建目录内的临时配置：

```bash
python3 engine/tests/inference/run_core_placement_reload.py \
  --binary /path/to/new-engine --app /path/to/isolated-app \
  --config /path/to/three-channels.json --output /path/to/new-private-reload-report
```

该测试依次覆盖固定 → 部分自动 → 只改其他通道核心 → 三路自动 → 固定，
再注入一个路径存在但无法初始化的模型，验证旧模型与自动核心池一起回退并继续出帧。
初始化失败是此项测试的预期行为，不计作正常性能测试零错误的证据。
