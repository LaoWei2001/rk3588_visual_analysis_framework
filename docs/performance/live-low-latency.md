# 实时画面与检测结果低延迟调整（2026-11-03）

历史实测：2026-11-03。下文部署状态和测量结果仅描述当时那次实验。当前播放参数可核对 `web_console/frontend/src/pages/livePlayback.ts` 与 `web_console/backend/routers/stream.py`。

本轮同时检查 HDMI、直接 RTSP 和 Web。测试使用当时的 **9 路、3×3、1920×1920** 配置，
保留硬件解码、模型、SORT 跟踪、HDMI 显示和 H.264 硬件输出。

## 实际改动

- Web 常态播放缓冲从 300 ms 降到 100 ms；短时断粮后的临时缓冲上限从 600 ms 降到 300 ms，稳定后继续回落。
- 更早小幅加速追赶；落后最新连续区间超过 500 ms 时跳回实时位置附近，保持断流重连和配额回收逻辑。
- H.264 保持零转码，fMP4 分片目标从 100 ms 降到 33.333 ms。实际分片只能在帧边界生成，不保证每片恰好 33.333 ms。
- 分片变小后，HTTP 队列槽位增加到 96；原有 **3 秒、4 MiB** 的队列上限继续生效，避免短暂抖动因分片数量增加而被错误断开。
- 实时 RTSP 输入抖动缓冲从 80 ms 降到 40 ms，appsink 只留一帧；本地文件的按时间戳播放逻辑不变。
- 输出 appsrc 和编码前队列各只允许一帧待处理数据，限制编码受阻时积压的旧画面。保留非阻塞提交和安全的 DMA 缓冲池。
- 当时被测应用每路推理 worker 从 3 个改为 1 个，减少等待 NPU 的旧帧和结果排队。

HDMI 的 16 ms 刷新候选没有取得稳定收益，反而增加了本机负担，已撤回；保留原来的 33 ms 刷新。
预览本来就显示最新解码帧，推理与预览并行，因此减少 worker 主要改善检测结果的新鲜度，不能把它等同于整张画面的传输延迟。

## 三种观看路径的帧龄

使用 320×180@30 的合成 RTSP 源，在图像内编码生产者的单调时钟。它经过实际引擎的
9 路推理、RGA 拼接和硬件编码，再从客户端真正解码或显示的像素中读回时间码。
HDMI 用本机 X11 窗口像素采样；直接 RTSP 用本机低缓冲 GStreamer 硬解客户端；Web 用真实 Chromium、实际后端路由和发布构建。

新旧对照均同时运行这些出口。Web 连续注入三次 1.1 秒 HTTP 暂停，等待 10 秒恢复，再采样。
这是**合成源到软件显示链路**的实测，不含现场摄像头曝光/ISP、外部网络以及物理显示器扫描响应时间。

| 路径 | 调整前 P50 / P95 | 调整后 P50 / P95 |
| --- | ---: | ---: |
| HDMI 窗口 | 102 / 129 ms | 104 / 141 ms |
| 直接 RTSP | 98 / 125 ms | 100 / 123 ms |
| Web，卡顿恢复后 | 604 / 644 ms | 482 / 570 ms |

Web 中位数降低约 20%。HDMI 和直接 RTSP 的常态延迟没有测出明确改善，仍约百毫秒；缩短队列主要限制拥塞时的积压。
Web 两轮均只建立一次视频连接，短时暂停后正常恢复，没有靠反复断开重连追赶。
CPU 调频没有锁定，表中为单轮对照，不能把几毫秒差异当作稳定收益。

## 真实摄像头与 9 路业务

另外用原摄像头分别预热 15 秒、测量 45 秒，保留 HDMI 和实际连接客户端的 RTSP 硬件输出。
摄像头只读检查得到 H.264、1280×720、25 FPS，流元数据 `has_b_frames=0`；没有修改摄像头的编码或画质配置。

| 指标 | 原版、每路 3 worker | 新版、每路 1 worker |
| --- | ---: | ---: |
| 总成功推理及发布 FPS | 172.48 | 171.57 |
| 平均入队到处理完成 | 175.38 ms | 72.20 ms |
| 进程峰值 RSS | 600.1 MiB | 381.2 MiB |

结果排队处理耗时降低约 59%，吞吐下降约 0.5%。两轮每路输入解码均约 25 FPS，测量期间无推理失败，RTSP 持续输出且程序正常退出。
这说明当时被测的多路配置适合减少 worker；单路、少路或其他模型应重新测量，不能一律套用。

## 用其他播放器观看

设备端无法替远端播放器修改缓存。VLC 可以先以 80 ms 网络缓存、TCP 播放；网络抖动明显时再适当增加。
该缓存参数和 TCP 选项可参考 [MediaMTX 官方 VLC 播放示例](https://mediamtx.org/docs/features/rtsp-specific-features)。

```bash
vlc --network-caching=80 --rtsp-tcp rtsp://设备IP:8554/live
```

这是一组客户端参数，不是本轮实测过的 VLC 端到端延迟保证。上表的直接 RTSP 数据来自 GStreamer 客户端。
网页更新后需刷新页面，已有页面仍可能运行旧的播放器代码。
