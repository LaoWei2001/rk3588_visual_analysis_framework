# 程序故障恢复

入口为侧边栏“故障恢复 → 程序故障恢复”。与系统、网络恢复分别设置，默认两个开关均关闭。
设置适用于本设备通过程序管理启动的视觉应用；后台由 systemd 和平台运行库执行，关闭网页
不停止已启用的保护。

## 日常操作

1. 按需打开“程序退出后自动重启”：程序意外退出后默认等待 5 秒，使用原配置重新启动。
2. 如需识别程序仍运行但处理卡住，打开“程序卡住后自动恢复”。此开关会同时打开退出重启，
   避免检测到卡住后终止程序却无人重新启动。关闭退出重启会同时关闭卡住恢复。
3. 点击“保存设置”。保存不会结束或重新启动当前程序。
4. 当前程序需要应用新参数时，页面显示“重启程序并生效”；用户可点击立即生效，也可等待
   下次正常启动。立即应用会短暂中断视频与推理，不重启盒子。

没有运行中的程序也可保存，下次从程序管理启动时生效。程序管理页的开机自启是独立设置，
这里不会替用户打开自启、启动原本停止的程序，或修改系统/网络恢复策略。

页面分别显示当前程序和实际保护状态。“开关已保存”不等于当前运行实例已经生效；卡住检测
需要支持心跳协议的应用包，启动时检查能力。未生效时页面明确提示程序包可能不支持该功能，
不会将退出重启等同于业务卡死检测。旧程序包仍可使用退出重启。

## 高级设置

默认折叠，可按需修改：

| 设置 | 推荐值 | 范围 |
| --- | --- | --- |
| 退出后等待多久重启 | 5 秒 | 5～300 秒 |
| 单次处理多久未完成视为卡住 | 120 秒 | 30～1800 秒 |
| 启动或加载配置最多等待 | 300 秒 | 60～1800 秒 |

“恢复推荐时间”只调整三个时间，不改变两个开关。正常等待输入、暂停不计为执行中的业务
卡死。发现处理超时后停止服务心跳，再由 30 秒服务看门狗终止进程，按重启策略启动；表中
时间不是从故障到业务完全恢复的严格时限。只有接入进度标记的执行环节受内部超时监测。

分类切换和后台轮询保留未保存修改。其他页面改动了策略时提示重新读取；保存使用版本号
防止覆盖新配置，立即应用同时核对设置版本与当前程序，避免重启已经切换的其他程序。

## 实现和兼容

- `ApplicationRecoverySettingsSection.tsx`：两个日常开关、实际状态、高级参数与显式应用动作。
- `PUT /api/system/recovery/application`：只接受两个应用开关与三个等待时间，保留其他策略。
- `POST /api/system/recovery/application/apply`：提交 `{revision, app}`，核对后重启当前应用。
- 策略仍保存在 `/etc/rk3588-runtime/recovery.json`，应用下次启动时使用。
- 平台 `process_manager.py` 在显式启动应用时，自动清理本项目此前创建且内容匹配的
  `/run/systemd/system/<应用服务>.d/90-device-only-recovery.conf` 临时禁用配置，并重新加载
  systemd。用户无需通过 SSH 手动删除；管理员的其他覆盖配置保留。

应用恢复不会直接操作硬件看门狗，也不因普通应用崩溃重启整个盒子。系统和网络恢复见
[无人值守恢复](unattended-recovery.md)、[网络恢复](network-recovery.md)。

## 验证

```bash
python3 -m pytest services/framework/runtime_manager/tests services/framework/system_watchdog/tests -q
python3 -m pytest web_console/frontend/tests/test_recovery_settings.py -q
```

前端测试需先构建并具备 Playwright/Chromium，使用隔离接口，不改实际策略或重启当前应用。
`RK3588_SYSTEMD_TESTS=1` 可运行独立 systemd 集成测试，只操作可丢弃测试服务。
