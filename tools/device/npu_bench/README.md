# 模型独立推理测速

给这个工具一份 `.rknn` 模型，它会在 RK3588 上反复执行，测出：

- **单次推理延迟**：执行一次模型要多少毫秒。
- **设备推理吞吐**：多个模型工作副本一起运行，每秒合计完成多少次。

测试不启动摄像头、视频解码、图像缩放、网络或业务规则。只想知道“这个模型在这台设备上跑得多快”，就用它。

## 第一次使用

### 1. 进入目录，确认程序存在

```bash
cd /userdata/rk3588_visual_analysis_framework/tools/device/npu_bench
ls -l ./npu_bench
```

后续命令都在这个目录执行。仓库放在其他位置时，修改上面的路径。
如果没有 `npu_bench`，或刚修改过源码，编译一次：

```bash
./build.sh
```

可执行文件直接生成在当前目录。编译需要 `g++`、OpenSSL 开发库（提供 SHA-256）和仓库自带的 RKNN SDK。
在 Debian/Ubuntu 上，缺少 `openssl/sha.h` 或 `-lcrypto` 时需要安装 `libssl-dev`。

### 2. 停止其他推理程序，选好模型

先在 Web 控制台或对应终端正常停止正在运行的推理应用，让设备专门运行本次测试。
工具不会自动停止其他程序，也不会自动锁频。

下面以本机的 `projects/assets/yolov5s_relu.rknn` 为例，先确认文件存在：

```bash
ls -lh ../../../projects/assets/yolov5s_relu.rknn
```

没有这份文件时，把后续命令中的模型路径换成自己的、适用于 RK3588 的 `.rknn` 文件。
可以写完整路径；路径中有空格时加引号。

### 3. 先测“执行一次有多快”

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn
```

不加其他参数时，使用 **1 个实例、NPU 核心 0**。每轮先预热 3 秒，再正式测量 15 秒，共做 3 轮。
因此总共约需 **54 秒，加上初始化和收尾时间**。预热数据不算入结果。

只想先确认模型能运行，可以缩短测试：

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn --warmup 1 --seconds 3 --repeats 1
```

短测试用于确认操作流程；正式比较性能时应增加测量时长，并观察多轮波动。

### 4. 再测“整台设备每秒能完成多少次”

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn --mode throughput
```

吞吐模式默认创建 **3 个实例**，分别请求使用 NPU 核心 0、1、2。
实例就是同一个模型的独立工作副本：各自有输入输出内存，由各自的线程反复提交推理。
它不代表接入了 3 路视频。

想看增加到 6 个实例有没有收益：

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn --mode throughput --instances 6
```

这时每个核心会分到两个实例，具体执行由 RKNN Runtime 和驱动处理。
实例更多会增加内存占用，不保证更快。

## “纯推理”具体计了什么

默认测量范围是：**输入张量已准备好 → 同步执行模型 → 原生输出内存中的结果就绪。**

“张量”就是模型接收和产生的数据块。工具读取模型要求的类型、尺寸、排列和内存补齐规则，
提前申请并绑定全部输入输出内存，不再强制把每个模型当成 RGB8 图像模型。

| 工作 | 是否计入默认结果 |
| --- | --- |
| 读取模型、计算哈希、创建实例和线程、申请内存 | 否，在计时前完成 |
| 准备输入数据、图片预处理 | 否，输入在计时前准备好 |
| 正式测量前的预热 | 否 |
| RKNN 同步执行调用，直到原生输出就绪 | 是 |
| 模型内部必需的 CPU 算子，例如 CPU Transpose | 是 |
| 把原生输出取回成普通排列、复制输出 | 默认不做；可选 `--io readback` |
| 检测框解码、NMS、跟踪、业务规则和网络 | 不执行 |

模型需要的 CPU 计算也是推理成本，不能只把 NPU 算子的时间加起来当成模型总耗时。
原生输入避免的是额外输入适配，不会删除模型内部运算。

工具直接调用固定版本的 RKNN API，**不经过项目逐次推理的核心排队机制**。
保留项目的进程占用锁，防止与另一个框架推理进程同时运行。
正式测速不开逐层 profiling；逐层分析使用 [rknn_profile](../rknn_profile/README.md)。

## 结果怎么看

每轮结束会打印类似下面的结果。数字仅为**格式示例，不是实测成绩**：

```text
实例 0: 149 次 | 平均 20.000 ms | P50 19.800 ms | P95 21.000 ms
  执行 20.000 ms；输出取回及释放 0.000 ms；跨截止时间完成 1 次（不计吞吐）
本轮总吞吐: 49.667 次/秒；窗口 3.000 秒；收尾 10.000 ms
```

| 字段 | 怎么理解 |
| --- | --- |
| 平均耗时 | 窗口内完成的推理，其单次耗时的平均值；越小越快 |
| P50 | 一半耗时样本小于或等于这个值，表示常见水平 |
| P95 | 95% 的耗时样本小于或等于这个值，反映较慢情况 |
| 本轮总吞吐 | 所有实例在正式窗口内完成的次数，除以窗口秒数；越大越快 |
| 跨截止时间完成 | 截止时还在执行、之后才完成的任务，不算入本轮吞吐和延迟样本 |
| 收尾时间 | 窗口结束后等线程和在途任务退出的时间，不加到吞吐分母里 |
| 各轮范围 | 不同轮次吞吐的最小值和最大值，用来观察波动 |
| 测试有效 / 测试无效 | 初始化、核心设置、绑定、执行或释放错误都会让本次测试无效，并返回非零状态 |

各实例的延迟分别统计；多个实例并行时，总吞吐不能简单用 `1000 ÷ 某个实例平均耗时` 代替。
这里的单位是**模型执行次数/秒**，不是视频播放帧率；批量模型的一次执行可能处理多个样本。

每实例默认最多保留 100000 个延迟样本，超过后用固定种子的蓄水池抽样计算 P50/P95，
并明确标记“百分位抽样”。平均耗时、完成次数和吞吐仍使用全部有效数据。
极短窗口可能没有完整推理，此时会报错，请增加 `--seconds`。

## 常用参数

```text
./npu_bench 模型文件 [有名称的选项]
```

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `--mode latency` | 默认模式 | 只运行一个实例，关注单次延迟 |
| `--mode throughput` | 手动选择 | 多实例持续运行，关注设备总吞吐 |
| `--instances 6` | 延迟模式 1，吞吐模式 3 | 工作副本数；延迟模式只能填 1 |
| `--cores 0` | 延迟模式默认值 | 所有实例请求使用核心 0；也可填 `1` 或 `2` |
| `--cores 0,1,2` | 手动选择 | 每个实例请求三个核心的组合；也支持 `0,1` |
| `--cores round-robin` | 吞吐模式默认值 | 各实例依次请求使用核心 0、1、2、0…… |
| `--cores auto` | 手动选择 | 请求由 Runtime 自动选择核心 |
| `--warmup 3` | 3 秒 | 每轮预热时长 |
| `--seconds 15` | 15 秒 | 每轮正式窗口时长 |
| `--repeats 3` | 3 轮 | 重复测量次数，每轮都先预热 |
| `--io native` | 默认值 | 原生输入输出，计到模型执行完成 |
| `--io readback` | 手动选择 | 原生输入，再取回普通排列的输出，包含取回及释放时间 |
| `--timeout-ms 10000` | 10000 毫秒 | 一次阻塞推理的超时 |
| `--json result.json` | 不写文件 | 保存机器可读报告到当前目录 |

例如，对比一个模型同时使用三个核心时的单次速度：

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn --mode latency --cores 0,1,2
```

这仍然是一个模型实例，不等于三个单核实例。核心设置失败时会报错，
不会偷偷退回另一种设置后继续输出成功成绩。

旧的 `3 15 0 1` 数字参数已经取消，请改用上表中的选项。

## 需要把输出取回时

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn --io readback
```

该模式保持原生输入，但不绑定原生输出缓冲，使用 SDK 接口获取普通排列的输出，
保留模型原来的数据类型，不额外要求转成浮点数。结果分别给出执行调用、输出取回及释放的平均耗时。

由于输出绑定方式也不同，`native` 与 `readback` 的差值可能包含输出排列适配和内存管理，
不能直接当成“纯复制耗时”。比较结果时必须注明使用了哪种模式。

## 保存报告，记录测试条件

```bash
sudo ./npu_bench ../../../projects/assets/yolov5s_relu.rknn --mode throughput --json result.json
```

报告包含模型 SHA-256、实际加载的 Runtime 路径和 SHA-256、Runtime/驱动版本、核心配置、
输入输出属性、每轮结果，以及测量前后的 CPU/NPU/DDR 频率和调频策略、温度、系统负载。
环境数据是起止快照，不代表全程平均频率或最高温度。无法读取的信息会标记为不可用或不出现。

只有全部测试和资源释放成功，报告的 `valid` 才为 `true`。推理失败或按 `Ctrl+C` 中断时，
报告标记为无效，程序返回非零状态。重复使用同一个报告文件名会覆盖旧报告。

## 可选：提供实际输入数据或动态尺寸

默认将原生输入缓冲全部清零并反复使用。这适合测固定输入下的执行速度，不检查识别精度。
对输入值敏感的模型，应提供有代表性的实际输入张量，例如：

```bash
sudo ./npu_bench model.rknn --input 0:input0.bin --input 1:input1.bin
```

这些文件是**已按模型原生类型和排列准备好的二进制张量**，不是 JPG、PNG 或视频。
字节数必须与工具打印的原生输入内存大小一致，包含 stride/padding（为满足设备排列要求补齐的空间）。
未指定的输入仍清零。所有文件读取和准备都在正式计时前完成。

动态尺寸模型必须显式选择输入形状，例如：

```bash
sudo ./npu_bench model.rknn --shape 0:1x3x640x640
```

`0` 是输入编号，后面按该输入的逻辑维度顺序填写。多个动态输入分别指定。
当前锁定 SDK 没有专门查询“当前动态形状的原生属性”的接口，因此只接受能与当前逻辑形状
严格核对一致的原生输入输出；无法核对的动态布局会明确拒绝，不猜测缓冲大小。
模型支持范围以实际 SDK 返回结果为准。

## 常见问题

| 提示 | 怎么处理 |
| --- | --- |
| `No such file or directory` | 确认目录、程序和模型路径；需要时执行 `./build.sh` |
| `NPU is owned by another inference process` | 正常停止另一个框架应用或测试，再重试；不要删除占用锁文件 |
| `Permission denied` | 用 `sudo` 执行 |
| `set core mask failed` | 模型/驱动不支持请求的核心方式，改用支持的方式重测 |
| `query tensor`、`bind native tensor` 失败 | 当前模型或 SDK 不支持这条原生 I/O 路径，本轮无有效成绩 |
| `Native input needs exactly ... bytes` | 输入大小不匹配，检查原生类型、排列和补齐空间 |
| `Dynamic input ... needs --shape` | 为相应动态输入填写形状 |
| `Pinned SDK cannot verify ...` | 无法确认动态原生布局，本轮不能当作成功测试 |
| `No completed inference in window` | 窗口短于模型耗时或排队时间，增加 `--seconds` |
| `rknn_run` / `get outputs` 失败 | 保留完整报错排查，失败结果不用于比较 |

诊断具体慢算子使用 [rknn_profile](../rknn_profile/README.md)；
查看或调整频率使用 [npu_freq](../npu_freq/README.md)。测速工具不会自动修改频率。
比较多次结果时，使用同一模型、输入、核心配置、Runtime 和相近的温度、频率条件。

开发回归从仓库根目录运行：

```bash
python3 -m pytest -q tools/device/npu_bench/tests/test_npu_bench.py
```

它使用可控的模拟 SDK 验证计时、原生布局和错误处理，不占用真实 NPU。
