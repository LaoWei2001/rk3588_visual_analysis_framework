# 设备频率查看与定频工具

`npu_freq.sh` 可以查看 RK3588 当前的频率和温度，也可以在测速时临时固定频率，
帮助比较“速度变化是否和频率有关”。**第一次使用，先运行 `status` 查看状态即可。**

虽然名字里写着 NPU，但它会操作三部分：CPU（运行普通程序的处理器）、
NPU（执行模型的处理器）、DDR（内存）。`lock` 会尝试同时固定这三部分的频率。

这是一个可以直接运行的 Shell 脚本，**无需编译，也没有 `build.sh`**。

## 第一步：进入目录，查看状态

在 RK3588 设备的终端里执行：

```bash
cd /userdata/rk3588_visual_analysis_framework/tools/device/npu_freq
sudo ./npu_freq.sh status
```

下面的命令都在这个目录执行。仓库放在其他位置时，修改上面的路径。
`status` 只读取信息，不改变频率；省略 `status`、直接运行脚本也会查看状态。

## 输出怎么看

输出会分成 CPU、NPU、DDR 和温度几部分。下面只是**格式示例，不是当前设备的读数**：

```text
===== CPU =====
  policy0  gov=schedutil    cur=1800000 kHz  max_avail=1800000 kHz
===== NPU (...) =====
  gov=ondemand     cur=950000000 Hz  max_avail=1000000000 Hz
```

| 字段 | 怎么理解 |
| --- | --- |
| `policy0` 等 | 一组共用调频设置的 CPU 核心，所以可能出现多行 CPU 信息 |
| `gov` | 当前调频策略，代码里叫 governor。自动策略会按负载调整频率；本脚本锁频时会把它设为 `userspace`，由程序指定目标频率 |
| `cur` | 读取状态时的当前频率 |
| `max_avail` | 系统提供的可用频率中，最高的那一档 |
| 温度中的 `C` | 摄氏度，各行是设备不同温度传感器的读数 |

单位要分清：CPU 的 `1800000 kHz` 是 **1.8 GHz**；NPU 的 `950000000 Hz` 是 **950 MHz**。
这里看到的是读取时的状态，不是整段测速期间的平均值。

## 第二步：确实需要做频率对比时，再锁频

如果只是普通测速，不需要锁频。要做频率对照，先按
[npu_bench 的说明](../npu_bench/README.md)准备好程序、选择模型，并停止其他推理应用。
然后留在当前 `npu_freq` 目录，通过相邻目录的程序测一次，记下未锁频时的结果：

```bash
sudo ../npu_bench/npu_bench ../../../projects/assets/yolov5s_relu.rknn --mode throughput --seconds 15 --repeats 3
```

上面的模型路径按实际文件替换。测完后，再执行锁频命令：

```bash
sudo ./npu_freq.sh lock
```

这条命令会：

1. 把原来的调频策略备份到 `/tmp/npu_freq_saved.txt`。
2. 尝试把 CPU、NPU、DDR 的策略改成 `userspace`，默认设置到各自最高可用频率。
3. 打印修改后的频率和温度。

锁频后，仍在当前目录用**相同模型、相同参数**再测一次：

```bash
sudo ../npu_bench/npu_bench ../../../projects/assets/yolov5s_relu.rknn --mode throughput --seconds 15 --repeats 3
```

比较两次的“总吞吐”，测完按下一步恢复调频策略。
锁频会提高功耗和发热，适合有人观察的性能实验；不要因为执行了 `lock` 就认定已经设置成功，
还要查看后面打印的策略、实际频率和报错信息。

**一次实验只执行一次 `lock`。** 再次执行会覆盖原备份，导致 `restore` 无法恢复到第一次锁频前的策略。

## 第三步：实验结束，恢复调频策略

```bash
sudo ./npu_freq.sh restore
```

脚本读取备份，把原来的调频策略写回去，然后删除备份并打印状态。
检查输出和报错，确认恢复成功；如果原策略会自动调频，恢复后频率随负载变化是正常的。

关闭终端或按 `Ctrl+C` 不会自动撤销已经完成的锁频操作，实验结束后仍要执行 `restore`。
备份只记录“使用哪种调频策略”，**不记录原来手动指定的频率值**。
如果锁频前就已经使用 `userspace` 手工定频，原来的频率值需要你另行记录、手工恢复。

## 三个命令的区别

| 命令 | 做什么 | 是否修改设备设置 |
| --- | --- | --- |
| `sudo ./npu_freq.sh status` | 查看频率、策略和温度 | 否 |
| `sudo ./npu_freq.sh lock` | 备份策略，然后尝试固定 CPU/NPU/DDR 频率 | 是 |
| `sudo ./npu_freq.sh restore` | 用备份恢复原策略 | 是 |

## 可选：指定目标频率

不指定参数时，`lock` 使用最高可用频率。如果要指定其他频率，可以通过环境变量传入：

| 变量 | 控制什么 | 单位 |
| --- | --- | --- |
| `CPU_FREQ` | 所有 CPU 调频组尝试使用的频率 | kHz |
| `NPU_FREQ` | NPU 的目标频率 | Hz |
| `DMC_FREQ` | DDR 内存的目标频率 | Hz |

例如，假设你的板卡支持 NPU 900 MHz 和 DDR 1.56 GHz，可以执行：

```bash
sudo env NPU_FREQ=900000000 DMC_FREQ=1560000000 ./npu_freq.sh lock
```

这些数值只是写法示例，不是所有板卡都支持。`status` 只显示最高档，选其他档位前要查看
设备对应节点的 `available_frequencies`。没有指定的部分仍会尝试锁到最高频率；
所以上面的命令也会调整 CPU。`CPU_FREQ` 会应用到所有 CPU 调频组，各组都必须支持该数值。

## 常见问题

| 现象或提示 | 怎么处理 |
| --- | --- |
| `Permission denied` | 用 `sudo` 运行；如果是脚本本身没有执行权限，可先执行 `chmod +x ./npu_freq.sh` |
| NPU 或 DDR 后面没有路径，或频率为空 | 系统没有提供脚本预期的设备节点或频率列表，这部分信息无法读取，需要按板卡系统检查 |
| `lock` 后实际频率没有达到目标值 | 检查写入报错、是否支持 `userspace` 和目标档位；温度或系统限制也可能影响实际频率 |
| `未找到备份` | 尚未执行过 `lock`、已经恢复过，或临时文件已丢失。此时脚本无法知道原策略，不要把它当成恢复成功 |
| `restore` 时出现写入错误 | 恢复没有完成。脚本会删除备份，不能指望重复执行就能恢复，应根据事先记录的策略排查设备节点和权限 |

本脚本依赖板卡系统提供的 `/sys` 频率接口。它不是开机自动定频配置工具，也不会保存一套长期部署设置。
