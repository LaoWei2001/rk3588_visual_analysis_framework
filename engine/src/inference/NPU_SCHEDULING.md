# RKNN 核心调度

RK3588 上模型实例锁只保护一个 RKNN context，不能协调不同 worker、不同通道或不同模型类型。
现场驱动 0.9.0 在两个视频流各 3 worker、ZipDepth + YOLO26 Depth 同核并发时出现
`job abort ret=-22`、超时和无法正常停止；此前仅 ZipDepth 自身的锁未覆盖混合模型。

所有 7 个 RKNN 模型适配器现在通过 `npu_execution.h` 调用 inputs_set/run/get/release，
共用 `npu_core_gate.h` 的进程级状态，普通输入和 DMA 输入均受保护。
模型实例锁仍保护输入缓冲，同核锁保护从 SDK 输入提交到输出释放的完整周期。
输出描述符由 `npu::Outputs` 托管，即使后处理抛出异常也释放厂商缓冲。
不同明确核心可并行；未知 runtime AUTO 按三个核心全占用处理。
直接调用模型推理也使用同一保护，组合模型本身不重复持有核心锁，以免嵌套死锁。
核心掩码一次性申请，不会拿着部分核心等待其他核心；较早的重叠请求优先，避免饥饿。
停止或故障会唤醒所有排队请求，无需等正在运行的 ioctl 释放核心。
正常停止后可在空闲状态重新初始化；热更新和重新初始化都不会清除驱动故障标志。

## 全局核心规划

`npu_core=-1` 是框架自动规划，不是把每个 context 交给 Runtime AUTO。
旧的 `(channel_id + worker_index + model_index) % 3` 轮转不查看其他模型的显式分配，
会让耗时较长的模型占用其他通道的核心。2026-10-26 的 RTSP + USB 实机对照已复现此问题。

现在 `npu_core_assignment.h` 从完整配置建立静态计划，启动和热更新共用同一规则：

1. 收集启用且推理开启的通道中有效模型的显式核心 0/1/2；关闭模型不保留核心。
2. 自动模型先使用其余核心。一个自动分析通道可使用全部剩余核心。
3. 多个自动通道按通道 ID 排序；通道数等于可用核心数时，各有一个专用核心。
4. 其余情况在剩余核心内均衡轮转共享；所有核心均已显式指定时退回三核共享并打印提示。
5. 同帧子模型使用所属通道的核心池，worker/子模型在池内分配具体单核；显式指定仍优先。

| 配置 | 通道 0 | 通道 1 | 通道 2 |
| --- | --- | --- | --- |
| 自动 / 固定 1 / 固定 2 | 全部 worker 使用核心 0 | 核心 1 | 核心 2 |
| 三路全自动 | 核心 0 | 核心 1 | 核心 2 |
| 两路全自动，各 3 worker | worker 使用 0 / 1 / 2 | worker 使用 1 / 2 / 0 | 无 |
| 单路全自动，各 3 worker | worker 使用 0 / 1 / 2 | 无 | 无 |

通道 ID 不连续或配置数组重排不会改变专用核心排序。核心掩码 `0x1/0x2/0x4` 分别对应
核心 0/1/2。启动日志 `[NPU]` 给出池，实例日志给出 `requested_mask`；适配器仍需
记录实际接受的 mask，绑核失败不能被当成已隔离。分配只在初始化/模型热更新时计算，
不增加逐帧选核、轮询或切换 context 的成本；统一 SDK 保护没有放宽。

两路全自动保留三核均衡共享。实机 A/B 曾尝试两路各有专用核心并共享第三核，但不等长
队列增加重模型过期结果，发布率回退，因此未采用。需要严格分离两路预算时可显式指定核心，
不能将两路共享描述为互不影响。

显式分配的变化会重算其他未改动的自动通道。热更新仅在成功替换全部 worker 后记录
生效计划；某个模型加载失败时保留原实例，并根据回退后的配置再次协调自动通道。
重分配失败会明确报告保留旧实例、需要重启；热更新期间会暂停调度，不保证无缝切换。

这是通道资源隔离策略，不按模型耗时动态分配预算，也不保证各路相同 FPS。
重模型原先使用三核、现在仅剩一核时，其自身吞吐会下降，以恢复其他通道的预算；
不能同时承诺任意模型组合、每路原有三核吞吐和零等待。超过三个通道或显式指定同核时
资源竞争仍存在，由同核队列保证安全。[逐路对照和复现](../../../docs/npu-core-placement.md)。

任一 inputs_set/run/get/release 返回错误后，整个进程停止新的 NPU 提交，包括其他模型和核心。
原因是驱动超时恢复可能重置整个设备；已在途的 ioctl 无法在用户态强制取消。
恢复设备后需要重启推理进程；仅热更新模型不会清除失败状态。
`rknn_run` 请求 5000 ms 同步超时，但驱动卡住时不保证此时间内返回。
不在模型推理中自动执行设备重置。

正常引擎、硬件测试和基准程序使用 `/run/lock/rk3588-visual-npu.lock` 的进程占用锁，
第二个推理程序会在加载模型前退出，防止不同进程各自的核心锁彼此不可见。
元数据检查 CLI 只查询模型、不执行推理，仍可供运行中的 Web 编辑器使用。
这一锁约束更新后的本项目程序；旧二进制、外部 RKNN 程序不会自动遵守，须先停止或更新。

构建 `vision_analysis` 时自动执行 `check_npu_dispatch.py`：模型和 benchmark 中出现绕过
统一接口的原始提交调用会导致构建失败，后续新增模型也受此约束。

推理性能日志的 `rknn` 时间包含等待共享核心的时间，因此多路共享时该值高于模型独占核心的耗时。
实际吞吐请看每路 `infer_fps`，实际发布看 `publish_fps`；工作线程可能丢弃过时结果。

测试通过 `-DBUILD_ZIP_DEPTH_TESTS=ON` 构建：

```bash
cmake --build build/engine -j4 --target npu_core_gate_tests npu_execution_tests
cd build/engine
ctest --output-on-failure -R '^npu_'
```

CPU 测试覆盖跨编译单元互斥、9 种掩码（含 AUTO/ALL）的 81 种配对、七组并发任务压力、
不同核心并行、公平排队、停止/故障唤醒、输出异常释放、故障后阻止提交和跨进程占用。
全局规划用例另覆盖七类自动模型避让显式核心、关闭/无效项、稀疏 ID、数组重排、
一/二/三/六自动通道、混合组合模型、全核已指定、预案变化及回退后的重算。
真实硬件回归必须另行执行两个视频流，确认两路持续发布、RTSP 持续出帧，并验证正常停止；
仅测试一个模型或仅检查进程存活不足以验证混合调度。

`run_model_matrix.py` 可复现多路/同帧多模型、自动/固定核心以及两次热切换的板端验证。
输入 manifest 为模型配置节点数组，配置和日志写入独立目录，不改写用户配置：

```bash
python3 engine/tests/inference/run_model_matrix.py --binary build/engine/vision_analysis \
  --app /opt/ai_apps/test_depth --base-config /opt/ai_apps/test_depth/assets/depth_multi_model.json \
  --manifest /path/to/models.json --output /path/to/test-output
```

同帧所有子模型（包括不同尺寸的检测模型）均从源视频单独生成各自输入，结果映射回统一业务坐标，
无需检测模型彼此同尺寸。仍检查每个模型自身的输入/输出结构与适配器是否兼容。

## 历史回归（2026-10-26，旧轮转分配）

现场配置：两个 MP4 循环视频流，通道 0 为 768×768 FP16 ZipDepth，通道 1 为
640×640 YOLO26 Depth，每路 3 worker，queue_size=1；1280×720 RTSP 持续由 TCP 客户端解码。
测试只将 RTSP 端口改为 18554；第二轮另将两个模型均固定到核心 0。

| 场景 | 时长 | ZipDepth 推理 FPS | YOLO26 Depth 推理 FPS | 正常停止耗时 |
| --- | --- | --- | --- | --- |
| 两路自动分核 | 180 秒 | 6.60–7.68 | 6.56–7.76 | 1.28 秒 |
| 两路都固定核心 0 | 120 秒 | 2.36–2.70 | 2.30–2.65 | 2.02 秒 |

两轮失败数均为 0，RTSP 分别持续解码 5188 / 3527 帧，均正常退出（code=0）。
自动模式每路发布约 5.0–7.6 FPS；预览视频的帧率不等于推理结果的更新频率。
以上为本机有限时长回归，不代表所有模型和负载的长期稳定性保证。

## 历史组合排查（2026-10-26，全局规划之前）

新增防护后，本机 6 份权重全部参与测试：`yolov5s_relu`、`diaogou_s_107`、
`helmet_n1088_1011`、`helmet_n1088_1012`、`yolo26n-depth-float`、`zipdepth_npu_768x768-rk3588-fp16`。
输入包括 640 / 768 / 1088；每路 3 worker，最多 18 个上下文。

| 场景 | 有效运行时间 | 停止耗时 | 结果 |
| --- | --- | --- | --- |
| 六路视频，各一个模型，自动分核 | 120 秒 | 0.82 秒 | 全路零推理失败 |
| 六路视频，全部固定核心 0 | 60 秒 | 1.17 秒 | 全路零推理失败 |
| 同帧六个模型，自动分核 | 120 秒 | 1.07 秒 | 零推理失败 |
| 同帧六个模型，全部固定核心 0 | 60 秒 | 1.02 秒 | 零推理失败 |
| 同帧六模型，两次调整顺序并混用自动/核心 0/核心 2 | 120 秒 | 1.12 秒 | 两次热更新完成，零推理失败 |
| 注入一次 pthread_create 失败，验证串行回退与并行 worker 混跑 | 60 秒 | 1.02 秒 | 回退生效，零推理失败 |

所有场景持续解码 RTSP 且退出码为 0；六份权重另分别通过三个同核实例的普通输入与 DMA
入口测试（每份 48 次调用）。运行中启动第二个引擎或 benchmark，均在加载模型前被占用锁拒绝。
9 项调度/故障/跨进程/构建检查、模型状态与坐标回归、30 项后端模型校验测试通过。

这六份权重涵盖 YOLOv5 检测、YOLOv8 检测、YOLO26 Depth 和 ZipDepth。
YOLOv8 Pose、YOLO26 Pose、YOLOv5 Seg 的两种输入路径也已接入统一保护并参与编译检查，
当时没有这三类权重，未进行这三类的真实网络混跑；之后的全局规划回归范围见上方对照报告。
调度器的 81 种核心掩码配对与七组
并发任务测试不依赖模型种类，不能代替缺失权重的网络正确性测试。

普通/DMA 硬件入口测试可对任意受支持类型执行：

```bash

```

深度模型的标签参数传空字符串。线程失败注入仅用于测试：

## 性能验收

性能改动同时对比每路推理吞吐、发布吞吐和排队/处理耗时，不能只用合计推理 FPS 判断。
2026-10-26 较早的两轮输出/锁优化未通过严格的全通道发布性能验收，已经撤回；
测试方法、逐路数据及原因见 [NPU_PERFORMANCE.md](NPU_PERFORMANCE.md)。当前全局核心规划
保持原有 SDK 生命周期，另按资源预算与每路指标验收，见上方对照报告。
